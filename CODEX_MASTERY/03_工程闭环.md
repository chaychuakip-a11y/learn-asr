# 03：检查、修改、验证、审查

## 本课目标

学会判断 Codex 的实现是否真的完成，而不是只看最终回复是否自信。

## 1. 标准工程闭环

一次可靠改动通常包含：

1. 检查：读取说明、代码、测试、配置和当前 Git 状态。
2. 复现：对 bug 建立修复前可观察的失败。
3. 修改：做满足目标的最小一致性改动。
4. 验证：运行最贴近变更的检查。
5. 审查：查看 diff，寻找意外变化和遗漏。
6. 汇报：结果、证据、风险、未做事项。

“最小”是指范围与目标相称，不是为了少改而留下错误设计。

## 2. 先保护用户已有工作

一个仓库可能已有未提交改动。任务开始时应检查 Git 状态，区分：

- Codex 本次新产生的变化；
- 用户原有变化；
- 构建或测试生成的产物。

不要随意使用会覆盖工作的命令。看到陌生改动时，优先绕开；如果任务必须改同一区域且无法安全合并，再询问用户。

## 3. Bug 修复为什么要先复现

没有复现就修改，无法证明：

- 找到的是根因而非相似现象；
- 修改前问题确实存在；
- 新测试真的能捕获回归；
- 修改后通过不是因为测试根本没覆盖。

理想证据链：

```text
现有测试或最小复现失败
→ 定位错误状态首次出现的位置
→ 修改实现
→ 同一复现通过
→ 相关回归测试通过
```

## 4. 选择匹配风险的验证

| 改动 | 常见验证 |
|---|---|
| Markdown 文档 | 链接、路径、命令示例、diff |
| Python 函数 | 针对性单元测试、类型/静态检查 |
| 模块交互 | 集成测试、真实调用入口 |
| 模型导出 | 数值一致性、输入边界、运行时加载 |
| 服务接口 | 请求/响应契约、错误路径、并发或超时 |
| 部署配置 | 构建、启动、健康检查、回退方案 |

只运行一个无关测试，不能证明整个需求完成。全量测试通过也不自动证明新行为正确：测试可能没有覆盖它。

## 5. 如何阅读 diff

即使不会编程，也能先问六个问题：

1. 改动是否只出现在预期文件？
2. 有没有大量与目标无关的格式变化？
3. 有没有删除错误处理、断言或测试？
4. 有没有写入绝对路径、密钥、个人信息？
5. 新行为是否有相应测试或说明？
6. 是否出现二进制、模型、缓存等意外大文件？

可以让 Codex 自审：

```text
请审查你刚才产生的完整 diff，不要继续修改。逐项核对原始目标和完成标准；
重点寻找意外范围扩大、测试覆盖空洞、平台兼容问题和用户已有改动冲突。
区分“已验证”和“推测正确”。
```

自审有价值，但不能替代你的最终判断。高风险任务可以新开一个独立聊天审查，以减少原实现思路带来的偏见。

## 6. 测试失败时不要自动“修到绿”

失败可能来自：

- 本次代码缺陷；
- 旧有失败；
- 环境或依赖缺失；
- 测试本身错误；
- 数据或网络不可用。

正确做法是先分类。禁止通过删除测试、降低断言、吞掉异常等方式制造绿色结果，除非需求本身明确改变了预期行为，并有理由和新规格支持。

## 7. 最终汇报应该短但可审计

一个实用格式：

```text
结果：用户可观察到的变化。
文件：修改了哪些位置及原因。
验证：运行了哪些命令，结果是什么。
风险：没验证什么、有哪些边界或环境限制。
```

警惕模糊词：“全面优化”“彻底解决”“生产可用”。除非证据覆盖了这些广泛主张。

## 8. 实战：只读审计当前项目入口

在新聊天发送：

```text
只读审计当前仓库的“新用户最小运行路径”，不要改文件。

目标：确认 README.md 提供的环境安装、最小运行和测试步骤是否与当前代码一致。
上下文：检查 README.md、pyproject.toml、acoustic_engine/README.md、相关入口与测试。
约束：不联网，不下载，不运行模型训练；允许执行快速的 --help、导入检查或针对性测试。
完成标准：逐条列出已验证步骤、矛盾或缺口、对应文件证据和实际命令结果；
把“未运行”与“运行通过”严格区分。不要提出大范围重写。
```

审查它的报告后，再选择一个已证实的小缺口，另发修改任务。不要一次修完所有潜在问题。

## 本课验收

你需要保存一份完整记录，其中包含：

- 修改前事实或复现；
- 实际 diff；
- 至少一项针对性验证；
- 对未验证范围的诚实说明。

缺少任何一项，都不能声称完成了工程闭环。
