# 16：Hooks、自动化与 `codex exec`

## 本课目标

持久规则告诉 Codex“应该怎样做”，Hook 和 CI 可以机械执行检查，自动化可以按计划重复工作，`codex exec` 可以在没有交互界面的脚本中运行任务。本课教你在无人值守环境中保持最小权限、可观察性和失败安全。

## 1. 四种自动化不要混淆

| 机制 | 触发方式 | 适合 |
|---|---|---|
| Hook | Codex 生命周期事件 | 阻止秘密、注入上下文、事后检查 |
| Scheduled task | 时间或周期 | 定期报告、轮询、维护 |
| `codex exec` | 脚本/CI 主动调用 | 非交互分析、生成结构化输出 |
| CI 普通步骤 | Git/流水线事件 | 确定性构建、测试、lint、部署门禁 |

如果普通脚本能确定性完成，就不必让模型判断；如果需要理解自然语言、代码语义或非结构化信息，Codex 才可能有价值。

## 2. Hook 是什么

Hook 在 Codex 会话生命周期的指定事件运行自定义脚本。当前官方事件包括：

- 会话/子 agent 启动：`SessionStart`、`SubagentStart`；
- 轮次中：`PreToolUse`、`PermissionRequest`、`PostToolUse`、`PreCompact`、`PostCompact`、`UserPromptSubmit`、`SubagentStop`、`Stop`；
- 主线程结束：`SessionEnd`。

常见用途：

- 提示提交内容中疑似含 API key；
- 工具调用前检查命令策略；
- compact 前保存检查点；
- 工具完成后记录审计信息；
- 轮次停止时运行快速验证；
- 会话开始时加载本地任务说明。

## 3. Hook 不是万能拦截器

重要运行特性：

- 多个来源匹配的 hooks 都会运行；
- 同一事件多个命令 hook 可能并发启动，一个不能保证阻止另一个启动；
- 非托管命令 hook 需要审查和信任；
- Hook 脚本本身可能有 bug、泄露数据或拖慢每一轮；
- 项目 hook 只在项目配置被信任时加载。

因此，关键安全边界仍需沙箱、服务端鉴权、CI 和系统策略，不能只靠一个 Hook。

## 4. Hook 来源与信任

Hook 可以来自：

- 用户级 `~/.codex/hooks.json` 或用户配置；
- 项目 `.codex/hooks.json` 或项目配置；
- 启用的 Plugin；
- 系统或管理员托管配置。

多个来源会合并。非托管 Hook 的定义变化后，原信任可能失效，需要重新审查。CLI 中可用 `/hooks` 查看来源、信任或禁用；具体界面以当前版本为准。

审查 Hook 时关注：

- 完整命令和解释器路径；
- 输入从哪里来；
- 是否读取 prompt、代码、环境变量或密钥；
- 是否访问网络；
- 写入和日志位置；
- 超时与失败行为；
- 是否递归触发自身；
- 在 Windows/Linux 上是否兼容。

## 5. 最小 Hook 设计原则

1. 单一职责；
2. 快速、确定、可重复；
3. 输入和输出有结构；
4. 默认不泄露敏感内容；
5. 失败模式明确；
6. 有超时；
7. 日志不含密钥；
8. 脚本可独立测试；
9. 不把所有事件都绑定重型命令；
10. 配置和脚本纳入 review。

## 6. 什么时候用 Hook、AGENTS 或 Skill

| 需求 | 选择 |
|---|---|
| 告诉 Codex修改 Python 后要测试 | `AGENTS.md` |
| 自动拒绝提交中出现密钥模式 | Hook/CI scanner |
| 按固定步骤审计测试证据 | Skill |
| compact 前自动保存任务摘要 | Hook + 简单脚本/Skill |
| 每周一生成仓库报告 | Scheduled task |

文字规则适合指导判断，Hook 适合生命周期机械动作，Skill 适合完整方法。

## 7. Scheduled task 的成熟度门槛

只有手动运行已经稳定的工作流才适合调度。调度前：

- 连续手动成功多次；
- 输入来源稳定；
- 完成和停止条件明确；
- 输出有固定位置或通知渠道；
- 失败可见；
- 不需要临场高风险批准；
- 权限和凭证最小化；
- 重复执行是幂等或能防重复。

“我不想再手动调试这个不稳定提示词”不是调度理由。

## 8. 独立任务还是现有聊天内任务

- 独立 scheduled task：每次运行彼此独立，适合日报、定期扫描。
- 现有聊天内定时任务：需要保留原聊天上下文，适合轮询长任务或持续 review。

桌面应用中，本地项目任务需要电脑和应用保持运行；Git 项目可以选择本地目录或独立 worktree。Web 定时任务不能直接访问你的本地文件夹，需要上传、项目来源或 connector。

## 9. 无人值守权限

Scheduled task 无法像你坐在旁边时随时判断批准。原则：

- 默认 read only；
- 确实要改仓库才 workspace write；
- 使用 worktree 隔离后台修改；
- full access 只用于受控隔离环境；
- 外部写入设置精确目标和服务端权限；
- 不允许任务自行扩大范围；
- 每次运行记录版本、输入、动作和结果。

自动任务使用的 prompt 也要抗时间变化：不能依赖“刚才那个文件”或“最新情况”而不定义来源。

## 10. `codex exec` 的用途

`codex exec` 在脚本或 CI 中非交互运行 Codex。适合：

- 生成提交或发布摘要；
- 对仓库做只读语义检查；
- 输出给其他脚本的结构化结果；
- 在流水线中执行预设 sandbox 和审批策略。

基础示例：

```powershell
codex exec "只读总结当前仓库结构，并列出 5 个需要验证的风险。"
```

默认非交互模式是只读沙箱；需要编辑时应显式选择工作区写入。不要从教学示例直接升级到 full access。

## 11. stdout、stderr 与结构化输出

非交互模式中，进度通常写入 stderr，最终 agent 消息写入 stdout，方便管道处理。

机器消费时使用 JSONL 或 JSON Schema，而不是解析自然语言段落。结构化输出应验证：

- 必需字段；
- 类型；
- `additionalProperties` 策略；
- 失败事件和退出码；
- 不完整结果；
- schema 版本。

概念示例：

```powershell
codex exec --json "审计仓库并输出事件流"
codex exec "提取项目元数据" --output-schema .\schema.json -o .\metadata.json
```

实际参数以当前 CLI `--help` 和官方文档为准。

## 12. 自动化中的认证安全

不要：

- 把 API key 提交到仓库；
- 把认证文件复制到 issue 或日志；
- 将宽权限 key 暴露给运行不受信任仓库脚本的整个 job；
- 在 PR 来自外部贡献者时默认暴露 secret；
- 把模型输出直接当 shell 命令执行。

应当：

- 使用 CI secret store；
- 仅在单个受控步骤注入凭证；
- 限制 scope、时间和环境；
- 对外部写动作设置服务端鉴权和审计；
- 使用隔离 runner/container；
- 失败后撤销或轮换可疑凭证。

## 13. 自动化可观察性

每次运行至少记录：

- 工作流版本和 prompt/Skill 版本；
- 仓库提交或输入版本；
- 模型与关键配置（不含秘密）；
- 开始、结束和退出状态；
- 工具动作摘要；
- 验证结果；
- 产生的 diff/产物；
- 未处理风险；
- token、时间或成本（需要时）。

只保存最终一句“成功”无法排查误报和回归。

## 14. 失败安全与幂等

定时和 CI 可能重复运行。设计时问：

- 同一输入运行两次会不会发送两封消息或创建两个 issue？
- 中途失败后重试会不会覆盖正确产物？
- 能否使用输入版本作为幂等键？
- 部分成功如何恢复？
- 何时停止自动重试并通知人？

对于外部写操作，优先“生成草稿/预览→人工确认→执行”，除非流程已经成熟且权限严格。

## 15. 第一个自动化练习：只读课程审计

先手工验证 prompt：

```text
只读审计 CODEX_MASTERY。检查 01–16 章节导航、内部链接、代码围栏、
每章是否有目标/实战或练习/验收，以及 README 发布状态。
输出结构化摘要：检查项、通过数、失败列表、无法验证项。
不修改文件，不联网，不运行训练。
```

连续手工运行并确认稳定后，才设计 `codex exec`：

- read-only sandbox；
- 固定仓库根目录；
- JSON Schema 输出；
- 非零失败状态处理；
- 结果写入临时或 CI artifact，不修改教程；
- 发现问题只报告，不自动修复。

这是一条适合初学者的自动化，因为没有外部写入，失败易观察。

## 16. Hook 设计练习

设计一个 `PreCompact` 检查点 Hook，但先不要安装：

```text
输入：当前任务摘要、工作目录、Git 状态。
输出：写入用户本地日志目录的时间戳检查点。
约束：不读取文件内容、不记录 prompt 全文、不访问网络、不包含环境变量值；
3 秒超时，失败只警告不破坏当前聊天。
```

要求 Codex先给威胁模型、跨平台路径方案、单元测试和卸载方法。只有脚本独立测试通过、配置 diff 审查通过后才信任 Hook。

## 17. 阶段 D 综合验收

提交以下设计和至少一项安全实作：

1. 一个经过正/反例验证的 `AGENTS.md` 草案；
2. 6 个场景的最小权限矩阵；
3. 一个用 `$skill-creator` 制作并通过触发测试的个人 Skill；
4. Skill/Plugin/MCP 的选择说明；
5. 一个只读、结构化的 `codex exec` 练习，或等价设计；
6. 一个 Hook/自动化威胁模型；
7. 逐项说明哪些内容没有实际安装或运行。

## 评分表

每项 0–2 分，共 20 分：

| 项目 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 持久化层 | 全塞提示词 | 大致区分 | Prompt/AGENTS/Skill/Hook/CI 边界准确 |
| AGENTS | 口号堆积 | 有命令 | 范围、命令、验证且正反例通过 |
| 配置作用域 | 不清楚 | 会改全局 | 能按一次性/用户/项目/管理员选择 |
| 权限 | 默认全开 | 有风险意识 | 每项任务最小授权且可解释 |
| Skill | 描述宽泛 | 能手动用 | 自动/显式触发正确且失败处理完整 |
| MCP/Plugin | 混淆 | 知道定义 | 能按实时工具与分发需要正确选型 |
| Hook | 未审查安装 | 有脚本 | 威胁模型、信任、超时、卸载均完整 |
| 自动化 | 手动未稳定即调度 | 可运行 | 稳定、幂等、失败可见、权限最小 |
| 结构化输出 | 解析自然语言 | 有 JSON | schema、错误、版本均验证 |
| 安全证据 | 只说安全 | 有清单 | 凭证、外部写、日志、恢复均有证据 |

达到 16 分，且“权限、Skill、Hook、自动化”均不为 0，阶段 D 通过。

## 本课口试

1. Hook、Skill 和 CI 分别解决什么？
2. 为什么多个匹配 Hook 不能互相当作串行拦截器？
3. 为什么手动不稳定的流程不能直接调度？
4. `codex exec` 为什么默认从只读开始？
5. 无人值守外部写操作怎样保证幂等和可审计？

能设计一条失败安全、最小权限、可观察的自动化，而不是只让它“定时跑起来”，才算掌握。
