# 02：从“提问”升级为“任务说明”

## 本课目标

把一个模糊想法写成 Codex 可以自主执行、边界明确、结果可验收的任务说明。

## 1. 好提示词不等于长提示词

新手常见两个极端：

- 太短：“优化一下项目。”
- 太满：提前规定几十个实现步骤，让 Codex无法根据仓库事实调整。

有效提示词让“结果”清晰，让“实现路径”保留合理空间。

通用模板：

```text
目标：<用户能观察到的结果>

上下文：
- <相关文件、错误、命令、截图、复现步骤>
- <为什么现在要做>

约束：
- <兼容性、安全、范围、不可改变的行为>
- <允许或禁止的外部动作>

完成标准：
- <必须通过的测试或命令>
- <必须出现或消失的行为>
- <最终汇报需要包含什么>
```

你不必每次写标题，但脑中必须有这四类信息。

## 2. 用可观察结果描述目标

较弱：

```text
把测试搞好一点。
```

较强：

```text
修复 tests/test_learning_path.py 当前的失败，使测试在 Windows PowerShell
环境下通过，同时不降低原有断言强度。
```

第二个目标说明了对象、结果、环境和禁止的“假修复”。

## 3. 给上下文，但不要伪造上下文

最有价值的上下文通常是：

- 完整错误信息和复现命令；
- 相关文件或目录；
- 期望行为与实际行为；
- 最近发生的变化；
- 一个正确示例；
- 用户真正关心的业务影响。

如果你不知道相关文件，可以把“找到相关文件”交给 Codex：

```text
我不知道实现位于哪里。请先搜索调用链和相关测试，用证据确定范围，
不要根据文件名猜测；确认根因后再修改。
```

## 4. 约束分三类

### 范围约束

例如“只改文档”“不要改公开 API”“不要重构无关代码”。它防止任务膨胀。

### 工程约束

例如“支持 Python 3.11”“沿用现有测试风格”“保持 Windows 路径兼容”。它保证方案能融入项目。

### 安全约束

例如“不要上传数据”“不要打印密钥”“不要删除产物”“任何外部写操作先询问”。它控制后果。

避免毫无必要地堆叠“绝对不准”。约束相互冲突时，Codex 只能猜。

## 5. 完成标准要能被验证

“代码更优雅”很难验收。下面更可验证：

- `pytest tests/test_acoustic_engine.py -q` 通过；
- 给无效 WAV 文件时返回明确错误，而不是 500；
- 不改变 `recognize()` 的参数和返回类型；
- `git diff` 中没有模型产物和数据文件；
- 文档中的三个示例命令能在 PowerShell 运行。

如果你不知道测试命令，可以要求 Codex 先从项目配置和文档找出正确命令。

## 6. 给复杂任务加“先调查”或“先计划”

适合直接执行：

- 单文件、低风险、行为明确；
- 已有测试覆盖；
- 失败容易恢复。

适合先计划：

- 多文件或跨模块；
- 需求仍模糊；
- 涉及迁移、架构、权限、生产环境；
- 存在多个成本差异明显的方案。

提示示例：

```text
先只读调查并给出计划，不要修改。计划需包含：当前状态证据、
根因或设计假设、拟改文件、风险、测试策略和仍需我决定的问题。
```

## 7. 让 Codex 访谈你

当你只有想法，没有规格时：

```text
我想给这个 ASR 项目增加一个供初学者使用的演示入口，但需求还模糊。
先不要编码。请像产品工程师一样访谈我，一次问最关键的 1–3 个问题；
指出会显著改变架构、工期或风险的选择。信息足够后输出可验收规格。
```

这比让 Codex 根据一句话直接造完整产品可靠得多。

## 8. 常用任务模板

### 解释代码

```text
面向只懂 Python 基础的读者，解释 acoustic_engine/decoder.py。
先概括输入输出和调用位置，再按执行顺序解释关键函数。
每个结论引用具体符号；不要修改文件。最后给 3 道自测题。
```

### 诊断问题

```text
诊断 <现象>，先不要修复。使用 <复现命令> 复现，沿调用链找到最早
出现错误状态的位置。区分已证实事实与假设。输出根因、证据、影响范围、
最小修复方向；不能复现时说明缺少什么证据。
```

### 实施修改

```text
实现 <可观察结果>。先检查现有实现和测试，沿用项目风格，保留无关改动。
不要改变 <稳定接口>。新增或更新能在修复前失败、修复后通过的测试。
运行针对性检查，审查 diff，汇报文件、行为、测试结果和遗留风险。
```

### 代码审查

```text
审查当前未提交改动，不要修改。优先找会导致错误行为、数据损坏、安全问题
或兼容性回归的具体问题。每项给出严重级别、文件位置、触发条件和理由。
如果没有发现，明确说明并列出尚未覆盖的验证范围。
```

## 9. 迭代提示词，而不是重复说“再试试”

结果不理想时，指出具体差距：

```text
当前结果没有证明 Windows 下可运行。请补充 PowerShell 实际命令及输出；
不要重写已正确的实现。如果命令失败，先定位原因再决定是否修改。
```

有效反馈包含：观察到的差距、应保留的部分、新的完成标准。

## 练习

把下面三个模糊请求分别改写成 GCCD：

1. “优化识别速度。”
2. “README 看不懂，改改。”
3. “测试挂了，帮我看看。”

然后把你的版本交给 Codex，让它只做“任务说明审查”，从歧义、缺失上下文、冲突约束、不可验证标准四方面打分。不要让它执行任务。

## 本课验收

随机选当前仓库一个小目标。你的任务说明必须让另一位不了解前情的人回答：要得到什么、去哪里调查、不能破坏什么、如何证明完成。四项缺一项就继续修改。
