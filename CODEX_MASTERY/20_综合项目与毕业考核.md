# 20：综合项目与闭卷毕业考核

## 本课目标

毕业不是记住最多命令，而是能在真实仓库中把模糊需求变成安全、可验证、可交付的结果，并在 Codex 出错时主导纠偏。本章把前 19 课整合成一个完整项目和闭卷考核。

## 1. 推荐毕业实战项目

在 `G:\learn_asr` 为初学者交付一个“本地 WAV 识别演示与验收入口”。最终形态由需求访谈决定，可以复用现有 HTTP 服务、CLI 或最小本地页面，但必须产生真实用户价值。

最低用户故事：

```text
作为第一次接触 ASR 的学习者，
我希望使用仓库内已有模型和示例 WAV 完成一次识别，
看到识别文本、输入信息、耗时和可理解的错误，
并能依据文档重复运行和验证。
```

项目不默认要求训练新模型、公开部署、账户系统或云服务。

## 2. 为什么选择这个项目

它会同时用到：

- 仓库调查和调用链；
- 需求访谈和计划；
- Python/HTTP/音频/模型契约；
- 正常、边界和错误测试；
- 性能和可用性；
- Git/diff/review；
- 权限和安全；
- 文档；
- 长任务检查点；
- 可选 subagent；
- 完成审计。

范围足够真实，但可以切成小里程碑。

## 3. 不允许跳过的阶段

```text
P0 基线与安全边界
P1 需求访谈和规格
P2 架构/调用链与计划
P3 先建立验收测试或复现
P4 纵向最小实现
P5 错误、性能和安全加固
P6 文档与新用户复现
P7 独立 review 和修复
P8 完成审计与交付
```

每阶段都有证据门。不能因为 Codex 一次生成了大量代码就跳到 P8。

## 4. P0：基线

记录：

- 工作目录、分支、HEAD、Git 状态；
- 用户已有变化；
- Python/uv 环境；
- 当前快速测试命令、测试数量和退出码；
- 已有模型与样本是否可读；
- 禁止训练、下载、外部写入等初始边界；
- 任务检查点文件位置。

基线失败先分类。不要把旧有失败算作你的回归，也不要未经授权“清理工作树”。

## 5. P1：需求访谈和规格

Codex 每次问最多 3 个高价值问题。你必须决定：

- 目标用户和本地/部署范围；
- CLI、页面或 API 的入口；
- 输入来源、格式和大小；
- 模型如何选择或固定；
- 输出字段；
- 错误行为；
- 性能目标；
- 隐私和日志；
- 明确范围外。

规格至少有 8 个可观察验收条件。

## 6. P2：架构和计划

要求 Codex：

- 从真实入口建立调用链；
- 标注可复用组件；
- 列出模块和数据契约；
- 建立威胁模型；
- 提出不超过 6 个纵向里程碑；
- 每步有文件范围、测试、风险和回退；
- 指出需要用户决定的问题；
- 不先写代码。

若计划要求大规模重写已有引擎，必须有强证据；否则优先复用。

## 7. P3：测试设计

至少覆盖：

- 一个仓库内合法 WAV；
- 错误采样率或格式；
- 空/损坏输入；
- 模型缺失或加载失败；
- 输出 schema；
- 不泄露绝对路径/内部堆栈；
- 不触发训练和网络；
- 性能或耗时字段合理；
- 与现有 `AcousticEngine` 契约一致。

对每项写清证明什么、不能证明什么。适用时建立修复前失败。

## 8. P4：纵向最小实现

先实现一条最短端到端路径：

```text
选择示例 WAV
→ 使用已有 checkpoint
→ 调用现有引擎
→ 返回/显示结果
→ 有一个端到端验收测试
```

禁止先做大量 UI、配置和抽象。最短路径验证架构选择后，再扩展错误和可用性。

每个里程碑结束：

- 更新计划状态；
- 记录 diff；
- 运行针对性测试；
- 写检查点；
- 审查是否提前实施后续范围。

## 9. P5：加固

加入：

- 输入大小和格式边界；
- 稳定错误映射；
- 资源和超时考虑；
- 模型/文件来源边界；
- 日志脱敏；
- 相邻绕过测试；
- 性能基线；
- Windows PowerShell 兼容。

安全 finding 必须有代码路径和触发条件；不要用泛泛 checklist 代替实际审查。

## 10. P6：文档与新用户验证

文档至少包括：

- 前置条件；
- 环境和启动命令；
- 使用仓库样本的最小路径；
- 预期输出示例；
- 常见错误和排查；
- 测试命令；
- 不会上传/训练/持久保存什么；
- 已知限制。

最强验证是新聊天或另一位用户仅根据文档从干净环境执行。作者自己“看起来能懂”证据较弱。

## 11. P7：独立 review

使用 `/review`、新聊天或有界只读 subagents，从以下视角审查：

1. 正确性和音频/shape 契约；
2. 测试证据与失败路径；
3. 安全、隐私和资源耗尽；
4. 新用户文档和 Windows 命令；
5. 范围、无关改动和回退。

每项 finding 必须有严重度、位置、触发条件、错误行为和证据。你逐项接受、拒绝、验证或延后。

修复后重跑原验收和 review，不能只说“已处理评论”。

## 12. P8：完成审计

建立要求→证据矩阵：

| 要求 | 权威证据 | 状态 | 证明缺口 |
|---|---|---|---|
| 合法 WAV 可识别 | 端到端测试 + 实际命令输出 |  |  |
| 错误输入安全失败 | 错误路径测试 |  |  |
| 不训练/不联网 | diff、命令日志、权限记录 |  |  |
| 文档可复现 | 独立新用户运行 |  |  |
| 无高严重度问题 | 独立 review 及裁决 |  |  |

状态只允许：已证明、被反驳、部分、证据不足、缺失。任何必需项不是“已证明”，项目就不能宣称完整完成。

## 13. 推荐的主任务提示词

不要直接复制后无脑执行；先把尖括号内容替换成你的决定：

```text
/goal

目标：为 G:\learn_asr 交付一个 <CLI/本地页面/API> WAV 识别演示，
让 Python 初学者使用仓库已有 checkpoint 和示例音频完成识别，看到文本、输入信息、耗时和可理解错误。

当前边界：本地学习用途；不训练、不下载、不发布、不推送；保留 AcousticEngine
公开契约和现有用户改动。任何新生产依赖、外部写入或工作区外动作先询问。

完成标准：经过访谈确认的规格全部有证据；正常/边界/错误测试通过；
最小真实命令在 Windows PowerShell 运行；安全和 diff 独立 review 无未处理高严重度发现；
文档由新聊天按步骤复现；最终按原始要求逐项完成审计。

先执行 P0 基线和 P1 访谈，不要编码。建立持久检查点和动态计划；
每次只推进一个可验证里程碑，新事实改变方案时先更新计划。
```

如果当前界面不支持 `/goal`，删除命令行，保留完整自然语言目标。

## 14. 你必须亲自做的决策

Codex 可以建议，但以下不能全部外包：

- 产品范围；
- 风险接受；
- 外部权限；
- 新依赖；
- finding 裁决；
- 是否满足用户价值；
- 是否提交、推送、部署；
- 最终完成声明。

精通 Codex 的标志不是不做决定，而是用它快速获得做决定所需的证据。

## 15. 闭卷操作考试

不查看 01–19 正文，完成以下 10 项：

1. 为一个模糊需求写 GCCD；
2. 只读建立仓库调用链；
3. 诊断一个可复现失败但先不修；
4. 设计修复前失败的回归测试；
5. 实施最小修复并审查 diff；
6. 选择 new/resume/fork/compact 并解释；
7. 写一个 4 里程碑动态计划和恢复检查点；
8. 为两个 subagent 写有界委派契约；
9. 为一次外部数据访问设计最小权限；
10. 做逐要求完成审计并诚实保留证明缺口。

每项都要用实际输出或文件证据，不能只口头解释。

## 16. 理论口试题

随机抽 10 题：

1. GCCD 是什么？
2. 诊断为什么不自动授权修复？
3. 症状、错误传播点和根因的区别？
4. 全量测试通过为何仍可能证据不足？
5. `git diff` 为何可能漏未跟踪内容？
6. compact 与新聊天如何选择？
7. fork 为什么不等于文件隔离？
8. blocked 和困难有什么区别？
9. 何时值得使用 subagent？
10. `AGENTS.md` 与 Skill 的边界？
11. 沙箱与批准策略的区别？
12. MCP 与 Plugin 的区别？
13. Hook 为什么不能作为唯一安全防线？
14. 重构为什么需要特征测试？
15. Prompt injection 如何跨越工具边界？
16. 为什么锁文件不证明依赖安全？
17. A/B 评测为什么要冻结 rubric？
18. 什么证据支持“任务完成”？

每题 5 分，抽 10 题共 50；低于 40 分重学对应章节。

## 17. 综合项目评分表（100 分）

| 维度 | 分值 | 满分证据 |
|---|---:|---|
| 需求与范围 | 10 | 访谈、规格、范围外、8 个验收条件 |
| 仓库与架构 | 10 | 真实调用/依赖图和契约证据 |
| 计划与恢复 | 10 | 动态里程碑、两次检查点、一次恢复 |
| 实现质量 | 15 | 最小纵向实现、风格一致、无无关重构 |
| 测试证据 | 15 | 正常/边界/错误/集成、命令数量退出码 |
| Git 与 review | 10 | 基线、完整 diff、独立 findings 裁决 |
| 安全与隐私 | 10 | 威胁模型、输入/权限/日志/依赖闭环 |
| 文档与复现 | 10 | 新聊天或新用户从文档成功运行 |
| Codex 调度 | 5 | 正确使用计划、上下文、Skill/agent 等 |
| 完成审计 | 5 | 原始要求逐项映射权威证据 |

毕业线：总分至少 85；测试证据、安全、完成审计三项均不得低于各自 70%；没有未处理高严重度问题。

## 18. 失败后的重考

不需要重做全部项目。按失败类型回炉：

- 需求漂移：重学 02、09；
- 根因错误：重学 05、06；
- 测试空洞：重学 07；
- diff/回退问题：重学 08；
- 上下文丢失：重学 10、11；
- 协作冲突：重学 12；
- 持久化失控：重学 13–16；
- 架构大爆炸：重学 17；
- 安全越权：重学 14、18；
- 凭感觉选工作流：重学 19。

修复薄弱证据后重新审查相关维度。

## 19. 毕业后的持续精进

每月选择 3–5 个真实任务做复盘：

- 哪类提示最常失败；
- 哪条规则应该进入/移出 `AGENTS.md`；
- 哪个重复流程值得做 Skill；
- 哪个自动化仍需人工纠偏；
- 哪类 finding 误报最多；
- 模型、权限或工具更新是否使旧结论失效；
- 任务成功率、人工时间和风险是否改善。

精通不是终点，而是形成可测量的改进循环。

## 本课验收

只有同时满足以下条件才毕业：

- 综合项目达到 85/100；
- 闭卷操作 10 项全部有证据；
- 理论口试达到 40/50；
- 无未处理高严重度问题；
- 能从一次中断恢复；
- 能指出至少三个尚未验证或不能外推的结论；
- 最终交付由独立聊天盲审。

“Codex 说完成了”不计分。你能证明完成、识别缺口并作出风险决定，才是精通的开始。
