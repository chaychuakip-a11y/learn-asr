# 09：把模糊想法变成可执行计划

## 本课目标

简单任务可以直接执行；复杂任务若没有先澄清目标和决策，很容易“做得很多、做偏更多”。本课训练你让 Codex先调查、访谈、形成规格，再把规格变成可以持续更新的执行计划。

学完后，你应能：

1. 判断什么时候需要计划，什么时候直接执行更合适。
2. 用需求访谈发现真正会改变方案的决策点。
3. 区分目标、规格、计划、任务清单和进度汇报。
4. 用里程碑、证据和停止条件控制复杂工作。
5. 在计划变化时更新它，而不是悄悄偏离。

## 1. 五个容易混淆的东西

| 名称 | 回答的问题 | 示例 |
|---|---|---|
| 目标 | 最终为什么做、得到什么 | 初学者能从浏览器上传 WAV 并看到识别结果 |
| 规格 | 对外行为和边界是什么 | 仅接受 16 kHz 单声道 WAV，错误输入返回 400 |
| 计划 | 如何从当前状态到目标 | 调查入口→定义契约→实现→测试→文档 |
| 任务清单 | 当前有哪些动作 | 添加路由、写测试、更新说明 |
| 进度 | 哪些完成、证据是什么 | 路由完成；3 项契约测试通过 |

“先写个计划”如果没有目标和规格，只会得到一份看似整齐的动作清单。

## 2. 什么时候值得先计划

适合直接执行：

- 单文件或局部修改；
- 目标明确且已有测试；
- 风险低、容易回退；
- 不存在重要产品或架构选择。

适合先进入计划模式：

- 需要修改多个模块；
- 不确定当前实现或根因；
- 有多个差异明显的方案；
- 涉及数据迁移、公开 API、安全或部署；
- 验证成本高；
- 需求方自己也说不清要什么。

计划本身也有成本。不要让 Codex为一个错别字生成十步路线图。

## 3. 先让 Codex 调查事实

没有仓库证据的计划经常发明不存在的文件和接口。第一阶段提示词：

```text
进入计划阶段，先只读调查，不要修改文件。

目标设想：给当前 ASR 项目增加一个供初学者使用的本地演示入口，
能选择 WAV 并显示识别结果。

请先确认现有 CLI、HTTP 服务、模型加载、音频契约、测试方式和已有前端资产。
输出“当前状态事实、可复用能力、缺口、风险、仍需我决定的问题”。
每项引用文件或符号；不要提前选择技术方案。
```

这里最后一句很重要：调查阶段不应偷偷替你作产品决策。

## 4. 需求访谈只问高价值问题

Codex 不应该连续问几十个无关细节。高价值问题是不同答案会显著改变：

- 用户体验；
- 架构或依赖；
- 数据与安全边界；
- 工期；
- 验收方式。

例如：

1. 演示只供本机学习，还是会部署给他人访问？
2. 必须实时流式，还是上传整段 WAV 即可？
3. 模型路径由用户选择，还是使用仓库固定产物？

“按钮用蓝色还是绿色”通常不应在架构前成为阻塞问题。

访谈提示：

```text
一次只问最关键的 1–3 个问题。每个问题说明为什么会改变方案，
给出 2–3 个互斥选项、各自影响和你的推荐。不要问能从仓库直接查到的问题。
```

## 5. 把回答固化为可验收规格

规格至少覆盖：

- 用户与场景；
- 输入、输出和错误行为；
- 明确不做什么；
- 兼容性和性能要求；
- 安全与数据边界；
- 验收示例；
- 未决问题。

示例片段：

```text
用户：在 Windows 本机学习 ASR 的初学者。
输入：仓库内或本地选择的 16 kHz 单声道 WAV，最大 30 秒。
输出：数字文本、音频时长、推理耗时；识别失败显示可理解错误。
不做：账户、云上传、实时麦克风、生产部署。
验收：使用 data/spoken_digits_parts/7_jackson_0.wav 能返回结构完整的结果；
错误采样率返回明确错误，服务不崩溃。
```

规格中的数字和边界必须由用户决定或有现有证据支持，不能由 Codex随意编造。

## 6. 好计划的结构

每一步应包含：

1. 结果，而不只是动作；
2. 预计影响范围；
3. 依赖和顺序；
4. 验证证据；
5. 风险或停止条件。

示例：

```text
步骤 2：固定演示接口契约
- 结果：请求、成功响应和错误响应有可执行测试。
- 范围：deployment/app.py、相关测试；不改模型实现。
- 依赖：步骤 1 已确认现有 HTTP 路由。
- 验证：正常 WAV、错误采样率、缺失模型三类测试。
- 停止条件：若现有模型无法在测试内低成本加载，先设计依赖注入，不引入下载。
```

“修改后端”“完善测试”都太模糊，无法判断进度。

## 7. 计划必须动态更新

复杂任务中新事实会推翻原计划。正确流程：

```text
发现事实与计划冲突
→ 暂停受影响步骤
→ 说明证据和影响
→ 提出调整方案
→ 需要用户决策时询问
→ 更新计划后继续
```

错误做法是保留一份已失真的计划，同时暗中执行另一套方案。

给 Codex 的约束：

```text
每完成一步就用验证证据更新状态。若新事实改变范围、架构、安全或完成标准，
先更新计划并说明原因；不要为了保持原计划外观而继续错误路径。
```

## 8. Plan mode 与 Goal mode

在支持的 Codex 界面中：

- `/plan` 适合调查、访谈和形成方案；
- `/goal` 适合目标已经清晰、需要多步持续推进的工作；
- Goal 应包含结果、约束和验证标准；
- 工作过程中可以补充上下文、调整约束或请求状态摘要。

具体命令是否可用取决于当前 Codex 界面和版本。命令不可用时，直接用自然语言表达“先计划、不修改”或“持续推进直到满足以下完成标准”，核心方法不变。

## 9. 状态汇报不是重复计划

好的状态更新只回答：

- 已完成什么，可验证证据是什么；
- 正在做什么；
- 计划是否改变；
- 有什么风险或阻塞；
- 下一步是什么。

请求模板：

```text
给我一次状态审计，不要停下可安全继续的工作。
按“已完成及证据、当前步骤、计划变化、风险/阻塞、下一步”汇报。
不要把计划中的未完成项写成已经完成。
```

## 10. 防止计划常见失真

### 假完成

把“创建了文件”当成“功能完成”，但没有运行或测试。

### 永远在进行

步骤太大，例如“实现后端”，几小时都无法判断部分成果。

### 验证堆到最后

前面错误直到最后才暴露，返工范围巨大。

### 计划膨胀

发现任何小问题都加入当前目标，最终变成无限重构。

### 完成标准漂移

为了宣布完成，把原目标缩成当前已经做到的部分。

## 11. 实战：演示入口需求访谈

新开聊天并进入计划模式：

```text
我想给 G:\learn_asr 增加一个适合初学者的本地 WAV 识别演示入口，
但需求尚不清晰。先不要编码。

请先只读调查现有 deployment/、acoustic_engine/api.py、README 和测试；
然后一次问我最多 3 个高价值问题，挑战不现实的假设。
信息足够后输出：用户故事、范围外事项、接口/错误行为、风险、验收标准和分步计划。
计划每步必须有结果、范围、验证和停止条件。
```

你要实际回答访谈问题，但到计划完成后停止，不实施。审查计划是否引用真实仓库事实，是否把训练新模型错误地纳入一个演示入口目标。

## 12. 计划审查清单

- [ ] 目标描述用户结果，而不是技术动作。
- [ ] 规格区分范围内和范围外。
- [ ] 关键决定由用户作出或有证据支持。
- [ ] 计划引用当前仓库的真实文件和接口。
- [ ] 每步大小适中且有验证。
- [ ] 风险尽早暴露，验证不是全部留到最后。
- [ ] 有停止条件和回退点。
- [ ] 没有把计划本身冒充为实现完成。

## 本课验收

提交一份经过访谈的规格和计划，至少包含 3 个真正影响方案的决策、5 个可观察验收条件和 4 个带验证的执行步骤。

口试：

1. 目标、规格和计划有什么区别？
2. 为什么计划前要先调查仓库？
3. 什么问题值得打断用户询问？
4. 新事实推翻计划时应该怎么办？
5. 如何识别“假完成”？

只有能依据证据修改计划，而不是机械坚持原计划，才算通过。
