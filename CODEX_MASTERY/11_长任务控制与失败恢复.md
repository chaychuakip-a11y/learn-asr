# 11：长任务、检查点与失败恢复

## 本课目标

长任务的难点不是让 Codex“多工作一会儿”，而是让它在数十个步骤、工具失败、上下文压缩和中断之后，仍朝原目标推进，并能证明每个阶段的状态。

## 1. 什么叫长任务

以下任一特征都可能让任务变长：

- 多模块、多语言或多仓库；
- 需要大量调查和实验；
- 构建、训练或测试耗时；
- 有外部依赖或等待；
- 多个阶段分别需要验收；
- 中途可能需要用户决策；
- 不能在一次会话内稳定完成。

长任务不等于“大提示词”。它需要可恢复的执行结构。

## 2. 目标必须包含结果、约束和验证

在支持的界面中，可以用 `/goal` 启动持续目标；自然语言也可以表达相同契约。

弱目标：

```text
把部署做好，不要停。
```

强目标：

```text
让当前 ASR HTTP 服务能在本机使用固定测试模型处理 16 kHz WAV，
并为正常、错误采样率和模型缺失提供稳定响应。
保持现有 AcousticEngine 公共接口；不训练、不下载、不推送。
完成条件：相关单元/集成测试通过，服务启动检查通过，README 命令实际验证，
完整 diff 经 review 且没有未处理的高严重度发现。
```

“不要停”只表达持续性，不会自动赋予删除、发布、付费或修改外部系统的权限。

## 3. 里程碑必须产生可保存成果

推荐结构：

| 里程碑 | 可保存成果 | 完成证据 |
|---|---|---|
| M1 当前状态 | 调查报告/调用链 | 文件与符号证据 |
| M2 行为契约 | 规格和失败用例 | 用户确认、测试设计 |
| M3 最小实现 | 小范围 diff | 针对性测试 |
| M4 集成 | 可运行入口 | 集成测试/实际启动 |
| M5 交付 | 文档和最终 diff | 全量相关检查、review |

每个里程碑都应能在中断后独立理解。只有聊天中的“我差不多弄好了”不是检查点。

## 4. 检查点的最小内容

```text
任务目标与完成标准：
当前仓库/分支/提交：
已完成及证据：
已修改文件：
实际运行命令及结果：
当前进行中的步骤：
失败实验与已排除假设：
用户关键决定：
未解决风险/阻塞：
下一步：
恢复时第一项检查：
```

检查点应写入项目内专用计划或进度文件，但不要把临时绝对路径、密钥或敏感日志提交到仓库。

## 5. 按证据推进状态

任务状态常见误用：

- 文件创建了就标完成；
- 命令正在运行就标通过；
- 某个测试通过就标整个功能完成；
- 外部等待被写成“基本完成”；
- 为了结束而缩小原始目标。

状态规则：

- pending：尚未开始或缺少前置条件；
- in progress：正在执行，尚无完整完成证据；
- completed：该步结果和验证均满足；
- blocked：确有外部条件阻止继续，且安全替代路径已耗尽。

困难、耗时或暂时失败不等于 blocked。

## 6. 失败分类决定下一步

| 失败类型 | 示例 | 下一步 |
|---|---|---|
| 实现失败 | 断言与需求不符 | 诊断根因，修改并重测 |
| 环境失败 | 缺少依赖、端口被占 | 记录环境，选择安全替代或修复环境 |
| 工具失败 | 命令超时、输出截断 | 缩小命令、读取日志、续等而非重跑一切 |
| 数据失败 | 样本缺失或格式错误 | 校验数据来源和契约，不伪造通过 |
| 规格阻塞 | 两种行为需用户选择 | 给选项和影响，请求决定 |
| 权限阻塞 | 需要外部写入授权 | 说明精确动作、目标和风险，等待授权 |
| 旧有失败 | 基线本来就红 | 分离本次回归与旧问题，记录证据 |

同一命令连续失败时，先诊断，不要无限重试。

## 7. 耗时命令的管理

执行训练、构建或全量测试前，Codex 应说明：

- 为什么必须运行；
- 预计成本或时间；
- 可否先跑更窄检查；
- 产物写到哪里；
- 如何监控；
- 何时停止；
- 中断后能否恢复。

不要在没有信息增益的情况下反复启动同一耗时任务。先运行最小相关测试，再扩大验证。

## 8. 等待不是重新开始

后台任务仍在运行时，应继续等待同一任务并读取新增输出；重新启动可能产生重复训练、端口冲突或覆盖产物。

状态询问可以这样写：

```text
检查现有运行任务的新增输出和状态，不要启动第二份相同任务。
若仍运行，汇报最新检查点和异常信号后继续等待；
若结束，记录退出码、产物和验证结果。
```

长时间无输出不自动表示挂死。结合 CPU/GPU、日志时间戳、进程状态和任务性质判断。

## 9. 中断恢复协议

恢复时按顺序：

1. 读取最近检查点；
2. 确认工作目录、分支、HEAD、Git 状态；
3. 检查相关文件是否与记录一致；
4. 检查后台进程和端口，不盲目重启；
5. 验证关键产物存在且可读取；
6. 对过期事实重新验证；
7. 从最小下一步继续。

恢复提示词：

```text
恢复这个长任务。先只读对账最近检查点与当前工作树、Git 状态、相关进程和产物。
列出一致、变化、缺失、可能过期的内容；不要假设聊天中的“已完成”仍然成立。
更新计划后，从最小安全下一步继续。不要重跑已有昂贵步骤，除非证据显示产物无效。
```

## 10. 工作树隔离

Codex 桌面应用支持为 Git 项目创建独立 worktree，使不同聊天拥有独立文件副本，同时共享 Git 元数据。适合：

- 后台处理独立功能；
- 比较两个实现方案；
- 不打扰本地前台工作；
- 定时任务避免碰撞主工作区。

重要边界：

- 同一分支不能同时被两个 worktree 检出；
- ignored 文件默认不一定被带入；
- 每个 worktree 有自己的依赖和缓存成本；
- 聊天隔离不等于外部服务、数据库、端口也隔离；
- 合并回主线前仍要 review 和测试。

如果当前界面不支持托管 worktree，可以使用独立 Git 分支/工作树，但在尚未掌握 Git 前不要让 Codex自动执行复杂移动；先要求只读说明方案。

## 11. 完成审计

宣布完成前，从原始目标倒推证据：

```text
原始要求 1 → 哪个文件/行为/测试证明？
原始要求 2 → 哪个文件/行为/测试证明？
约束 A → diff 中如何确认没有违反？
完成标准 B → 实际命令、结果和覆盖范围？
```

对于每项标记：已证明、被证据反驳、部分完成、证据不足、缺失。只要必需项不是“已证明”，完整目标就没有完成。

## 12. 实战：多阶段只读审计目标

先练习不改代码的长任务：

```text
持续完成一次 ASR 课程可运行性审计，但不修改文件、不下载、不训练。

结果：为 README 中最小学习路径建立可验证报告。
范围：环境声明、前 3 个 notebook、acoustic_engine 最小测试、已有模型推理命令。
约束：先运行快速检查；单项预计超过 5 分钟时先说明成本；不覆盖任何产物。
验证：每个文档命令标注已运行/未运行、退出码、结果、环境限制。

请先建立里程碑和检查点格式，然后逐步推进。每个里程碑结束都更新证据；
工具失败先分类，不要重复运行。最终逐项审计原目标，不把未运行写成通过。
```

中途至少做一次暂停和恢复，观察 Codex是否先对账而不是重头执行。

## 13. 实战：故障恢复桌面推演

让 Codex给你五张情景卡，但先不要给答案：

- 测试运行 0 项却退出 0；
- 训练 20 分钟无日志；
- 恢复后发现 HEAD 改变；
- 端口被另一个服务占用；
- 外部数据下载需要新权限。

你为每张卡写：失败类型、第一项检查、禁止动作、可保存证据和继续条件。然后让 Codex依据本课规则评分。

## 本课验收

完成一个至少 4 个里程碑的任务演练，必须包含：

- 明确 Goal；
- 两次以上持久检查点；
- 一次暂停/恢复对账；
- 一次失败分类；
- 最终逐要求完成审计；
- 诚实记录未验证范围。

口试：为什么“不要停”不扩大权限？为什么任务仍运行时不应启动第二份？什么证据能支持真正完成？
