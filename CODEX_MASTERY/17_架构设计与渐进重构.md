# 17：架构设计与渐进式重构

## 本课目标

重构不是“让代码看起来更漂亮”，而是在保持既定行为的同时改善结构。架构修改更危险，因为影响跨模块、测试可能只覆盖局部、一次性大改很难审查和回退。本课训练你用 Codex完成证据驱动的渐进重构。

学完后，你应能：

1. 区分重构、功能修改、迁移和重写。
2. 在动代码前建立行为不变式和当前架构地图。
3. 把大改切成可独立验证、可审查、可回退的里程碑。
4. 设计兼容层、双轨验证和迁移终点。
5. 识别 Codex“顺手重构”和“大爆炸改写”的风险。

## 1. 四类变化先分清

| 类型 | 主要目标 | 行为是否变化 |
|---|---|---|
| 重构 | 改善内部结构 | 预期不变 |
| 功能修改 | 新增或改变用户行为 | 明确变化 |
| 迁移 | 从旧接口/格式/依赖转到新体系 | 过渡期可能双轨 |
| 重写 | 用新实现替换旧系统 | 风险最高，行为需重新证明 |

如果同时“重构解码器”和“改变 beam score 语义”，就不能只用重构测试标准。先分成行为变更与结构变更，分别审查。

## 2. 架构不是目录树

真正有用的架构地图包括：

- 用户入口；
- 模块职责；
- 数据流与控制流；
- 公共 API；
- 状态和生命周期；
- 外部依赖；
- 信任边界；
- 性能关键路径；
- 测试保护范围。

提示词：

```text
先只读建立当前架构地图，不要提出重构。
从用户入口沿实际调用追踪模块、状态、数据 shape、错误处理和测试；
区分公开契约、内部实现、推断和未验证项。找出循环依赖、重复职责和高耦合热点，
但每项必须有文件/符号证据。
```

先理解现状，再谈理想结构。

## 3. 行为不变式是重构契约

不变式描述重构前后必须保持的可观察事实。例如 ASR 系统：

- 相同合法波形和 checkpoint 得到相同 token 序列；
- 前端输出 shape、帧长计算和数值容差不变；
- 流式分块结果与不间断处理满足现有契约；
- 错误采样率继续被拒绝；
- checkpoint 字段和加载路径兼容；
- HTTP 响应 schema 不变；
- 性能不能超过已接受回归阈值。

不变式需要证据来源：公开文档、测试、类型、真实调用者或用户决定。

## 4. 先补特征测试

遗留代码测试不足时，直接重构会让你不知道什么被改变。特征测试（characterization test）先记录当前可观察行为，不代表当前行为完美，只为建立迁移基线。

流程：

```text
选择关键输入
→ 记录当前输出/错误/副作用
→ 判断哪些行为应保持、哪些是已知 bug
→ 为应保持行为写测试
→ 单独修复已知 bug
→ 再开始结构重构
```

不要把已知错误永久固化为“必须保持”。在测试名称或任务规格中明确哪些行为只是临时基线。

## 5. 找到 seam

Seam 是可以替换实现而不改动所有调用者的边界，例如：

- 一个接口或协议；
- 构造函数依赖注入；
- adapter；
- 纯函数边界；
- 文件格式读取层；
- 服务路由与核心引擎之间的契约。

Codex可先抽出 seam，再逐步迁移实现。好的 seam 应对应真实职责，不要为了测试而创造无意义抽象。

## 6. 纵向切片而不是横向大拆

危险计划：

```text
1. 重写所有模型
2. 重写所有调用者
3. 最后统一测试
```

渐进计划：

```text
M1 固定公开契约和特征测试
M2 引入兼容接口，旧实现仍作为默认
M3 迁移一个调用路径并双轨比较
M4 迁移剩余调用者，每批运行回归
M5 切换默认并保留短期回退开关
M6 删除旧路径、兼容层和死代码
```

每个里程碑都能独立合并、验证和回退。

## 7. 兼容层必须有删除计划

Adapter、feature flag 和双写可以降低迁移风险，也可能永远残留。设计时写清：

- 谁调用旧接口；
- 新旧映射规则；
- 警告或遥测；
- 默认何时切换；
- 删除前置条件；
- 最晚删除时间或版本；
- 回退策略。

“先加兼容层，以后再说”会制造永久复杂度。

## 8. 双轨验证

对高风险迁移，可让新旧路径处理相同输入并比较：

- 精确输出；
- 浮点容差；
- 错误类型；
- 状态转移；
- 延迟、内存和吞吐；
- 产物兼容。

双轨不是永远运行两套。定义样本集、允许差异、运行时间和退出条件。

## 9. 依赖图和循环

让 Codex调查：

- A 导入 B，B 是否又导入 A；
- 高层是否依赖低层具体实现；
- 配置、I/O、业务逻辑是否混在一起；
- 共享工具是否反向依赖业务模块；
- 类型和运行时导入是否可以分离。

不要仅凭目录名判断层次。使用真实 import、调用和测试证据。

## 10. 每个切片的验证阶梯

1. 新 seam 或 adapter 单元测试；
2. 被迁移调用者测试；
3. 新旧双轨样本；
4. 相邻模块集成测试；
5. 全量相关测试；
6. 性能/兼容/真实入口检查；
7. 独立 diff review。

失败时只回退当前切片，保留前面已验证里程碑。

## 11. 让 Codex 写重构计划

```text
先计划，不修改。

目标：将 <职责> 从 <当前模块> 中分离，以降低耦合并提高测试性。
约束：用户可观察行为、公开 API、checkpoint 和错误语义不变；不升级依赖；
不顺手清理无关代码。

请先建立当前调用/依赖图和行为不变式，指出证据缺口。
再提出按可独立合并的纵向切片计划。每个里程碑列：结果、拟改文件、
兼容策略、修复前基线、验证、回退和删除临时层的条件。
存在产品或架构决策时停下来询问，不自行扩大重构范围。
```

## 12. Codex 重构的常见失败模式

### 只看静态形状

移动类和文件，却漏掉运行时状态、序列化、插件发现或动态导入。

### 测试随实现一起改

新实现和新测试共同使用错误假设，旧用户行为没人验证。

### 无关清理膨胀

格式化全仓库、重命名公共符号、升级依赖，使 diff 无法审查。

### 兼容层双重真相

新旧路径逐渐产生不同配置和行为，却没有一致性检查。

### 一步到位

数十个文件一次替换，失败后难以判断根因和安全回退点。

## 13. 实战：声学前端职责重构计划

只做计划，不实施大改：

```text
只读调查 acoustic_engine/features.py、engine.py、训练入口、流式前端和相关测试。

假设目标：让音频加载、波形规范化、Log-Mel 配置和流式缓存职责更清楚，
但保持所有用户行为、feature 数值契约、训练/推理一致性和 checkpoint 兼容。

先判断这个目标是否真的需要重构；若证据不足可以拒绝。
若值得做，输出当前职责/依赖图、行为不变式、测试缺口、seam 候选，
以及最多 5 个可独立验证和回退的里程碑。不得直接修改。
```

你的任务是挑战计划：每个切片是否真的可单独合并？兼容层何时删除？是否漏掉训练路径？

## 14. 小型实施练习

从计划中只选第一个低风险切片，例如补特征测试或抽取纯函数。提示：

```text
只实施已批准计划的 M1，不开始 M2。先记录基线测试，再做最小 diff。
保持公开行为不变；运行 M1 针对性、相邻和全量相关测试；
比较修改前后输出，审查是否混入后续里程碑或无关清理。
若 M1 无法独立验证，停止并修订计划。
```

## 15. 阶段验收

提交一份重构方案和一个已实施的小切片，必须有：

- 当前架构与依赖证据；
- 明确的不变式和已知 bug 分离；
- 特征测试或基线；
- 纵向里程碑；
- 兼容层删除条件；
- 双轨或等价验证；
- 每步回退方案；
- 独立 review；
- 没有未授权行为变化。

## 本课验收

口试：

1. 重构和功能修改如何区分？
2. 为什么先写特征测试？
3. seam 有什么价值？
4. 兼容层为什么必须有删除条件？
5. 什么证据能证明一项重构保持行为？

能把一个“大重写”切成至少 4 个独立可验证、可回退里程碑，才算通过。
