# 10：聊天、项目、fork、side chat 与 compact

## 本课目标

上下文管理不是“聊天太长就 compact”这么简单。本课教你为不同结果选择正确的聊天结构，让 Codex保留必要决策，同时避免无关历史互相污染。

## 1. 项目、聊天和工作树分别保存什么

| 层级 | 主要作用 | 不应误解为 |
|---|---|---|
| 项目 | 组织相关聊天、文件和共享说明 | 一个无限长聊天 |
| 聊天/线程 | 保存一个连贯任务的对话与决策 | 仓库文件本身 |
| 工作目录/工作树 | 当前真实文件和 Git 状态 | 聊天历史的副本 |

聊天记录说“测试通过”，不代表你恢复聊天时当前工作树仍是同一版本。恢复任务时要同时检查聊天上下文和当前文件状态。

## 2. 一个连贯结果一个聊天

适合留在同一聊天：

- 对同一 bug 继续补充日志；
- 实现后要求补测试或审查；
- 根据 review 修复同一组发现；
- 对原目标调整非根本性约束；
- 请求状态摘要或解释当前实现。

适合新开聊天：

- 已经是另一个独立结果；
- 与原任务只共享仓库，不共享决策；
- 希望得到不受原实现思路影响的独立审查；
- 原聊天包含大量与新任务无关的信息。

错误模式：一个聊天里先修音频解码，再写营销文案，再研究数据库，最后回头部署。共享目录不等于共享任务。

## 3. `/compact` 的准确作用

在 Codex CLI 中，`/compact` 会把较早对话替换为简洁摘要，以释放上下文，同时尽量保留关键细节。

适合 compact：

- 同一任务仍继续；
- 已积累大量调查日志和工具输出；
- 核心目标、决策、约束和当前状态已经稳定；
- 你愿意先做一次检查点摘要。

不适合把 compact 当作：

- 清除错误指令；
- 回退文件；
- 切换到无关目标；
- 隐藏未解决冲突；
- 保存所有细节的无损压缩。

摘要会丢掉部分细节。重要契约、命令、决定和进度最好写入仓库文档、计划或学习记录。

## 4. compact 前的检查点

先要求：

```text
在 compact 前创建一次上下文检查点。只总结继续任务真正需要的信息：
原始目标、当前完成标准、关键用户决定、已改文件、验证命令与结果、
未解决问题、不得破坏的约束和下一步。区分已完成、进行中和待办。
如果聊天说法与当前工作树冲突，以实际文件和 Git 状态为准并指出冲突。
```

将关键内容写入 `LEARNING_LOG.md`、任务计划或专用进度文档后再 compact，更抗丢失。

## 5. `/new`：新的独立结果

`/new` 在 CLI 中开启新聊天，适合另一个独立目标。新聊天仍可处于同一个项目目录，因此能读取同一仓库，但不会自动继承旧聊天所有决策。

新聊天启动包应包含：

- 当前目标；
- 相关文件；
- 必须继承的决定和约束；
- 当前 Git 状态；
- 完成标准。

不要把“你应该知道前一个聊天”当作可靠上下文传递方式。

## 6. `/resume`：继续保存的原聊天

`/resume` 重新载入一个已保存聊天的历史。适合：

- 同一任务暂停后继续；
- 决策链仍然重要；
- 希望保留原问题、实验和反馈。

恢复后的第一步不是盲目继续，而是状态对账：

```text
先将保存的聊天状态与当前工作树对账，不要修改。
检查 Git 状态、相关文件和测试结果是否仍与上次检查点一致；
列出一致项、变化项、失效假设和建议下一步。
```

因为聊天暂停期间，用户或其他 agent 可能已经改过文件。

## 7. `/fork`：从共同历史探索不同分支

`/fork` 复制当前聊天到一个新聊天 ID，原聊天不变。适合：

- 从相同调查和规格比较方案 A/B；
- 保留稳定主线，同时探索风险较高的替代方案；
- 基于相同上下文进行独立审查或反方论证。

fork 的是聊天上下文，不自动保证代码文件彼此隔离。如果两个分支都写入同一工作树，仍然会冲突。需要并行写代码时，应使用独立工作树或严格分离文件和顺序。

## 8. `/side`：不打断主线的短问题

CLI 的 `/side` 创建临时侧聊，适合：

- “解释一下这个错误名”；
- “当前计划有什么明显风险”；
- “为什么选择这个测试命令”；
- 请求简短状态说明。

侧聊不适合承担长期实现或关键决策。关键结论需要回写主聊天或项目文档，否则主线可能看不到。

## 9. 选择矩阵

| 情况 | 选择 | 理由 |
|---|---|---|
| 同一 bug，日志变多 | 留在原聊天，必要时 compact | 保留推理链 |
| 暂停两天后继续同一功能 | resume + 状态对账 | 保留历史并校验文件 |
| 比较两个架构方案 | fork | 共享起点、分开探索 |
| 问一句不想扰动主线的问题 | side chat | 临时隔离 |
| 开始完全独立的文档任务 | new chat | 避免无关上下文 |
| 两个任务同时改同一文件 | 不直接并行 | 工作树冲突风险 |
| 独立 review | 新聊天或 detached review | 降低确认偏误 |

## 10. 上下文污染的信号

- Codex 把旧目标当成当前目标；
- 反复引用已推翻的决定；
- 把另一个任务的约束套进来；
- 忘记最新完成标准；
- 工具日志淹没重要决定；
- 最终汇报混合多个不相关结果。

修复顺序：

1. 明确指出当前目标和最新决定；
2. 要求基于工作树做状态审计；
3. 写检查点；
4. 同一目标继续则 compact；
5. 不同目标则新开聊天；
6. 原问题分支才 fork。

## 11. 文件是长期事实，聊天是工作记忆

应该写入文件的内容：

- 项目长期构建和测试规则；
- 已接受的架构决定；
- 接口契约；
- 多日任务计划和检查点；
- 可重复操作手册。

只适合留在聊天的内容：

- 临时探索；
- 已被排除的噪声假设；
- 一次性解释；
- 很快过期的中间输出。

后续第 13 课会进一步说明哪些持久规则应进入 `AGENTS.md`。

## 12. 实战：设计聊天拓扑

场景：你正在实现第 09 课的本地 WAV 演示，期间出现：

1. 需要比较 HTML 单页和 notebook 两种界面；
2. 想问 FastAPI 测试为什么使用 TestClient；
3. 另有 README 错别字；
4. 主任务积累了大量测试日志；
5. 希望独立审查当前实现。

先自己选择原聊天、compact、new、resume、fork 或 side，再让 Codex审查你的结构。参考方向：

- 方案比较：fork，但未隔离工作树前只读比较；
- 临时解释：side；
- 独立错别字：new；
- 主线日志过长：检查点后 compact；
- 独立审查：new/detached review。

不要机械照抄答案；说明每个选择如何保护上下文和文件。

## 13. 实战：compact 恢复演练

在一个已经有十轮以上交流的练习聊天中：

1. 让 Codex读取当前 Git 状态；
2. 生成 compact 前检查点；
3. 将关键进度写入学习记录；
4. 执行 `/compact`（若当前界面支持）；
5. compact 后要求复述目标、约束、完成项、待办和验证；
6. 对照检查点，记录丢失或改变的信息；
7. 补充缺失信息后继续一个小步骤。

如果界面不支持 `/compact`，让 Codex生成手工交接摘要，然后在新聊天粘贴，仍可练习上下文损失审计。

## 本课验收

给出五个真实或虚构场景，分别正确选择留在原聊天、compact、new、resume、fork、side 中的适当方式，并说明：

- 哪些上下文需要继承；
- 文件是否共享；
- 是否可能发生写冲突；
- 关键决定如何持久保存。

必须完成一次 compact 或手工交接恢复，并发现至少一项摘要可能遗漏的信息，才算通过。
