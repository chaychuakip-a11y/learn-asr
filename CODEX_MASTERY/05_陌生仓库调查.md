# 05：让 Codex 读懂陌生仓库

## 本课目标

你不需要先读完所有代码。本课训练你指挥 Codex 用最少但足够的读取，建立一张有证据、可继续追问的仓库地图。

学完后，你应能：

1. 确认 Codex 是否位于正确仓库和正确分支。
2. 从项目说明、配置、入口、核心调用链、测试五个层面调查代码库。
3. 区分文件清单、架构结论、实际运行事实和推断。
4. 控制调查范围，避免把整个仓库塞进上下文。

## 1. “读仓库”不是“逐文件总结”

低效做法：

```text
把这个仓库所有文件都读一遍，然后详细解释。
```

这会产生大量无关上下文。即使总结很长，也不一定回答你的真实问题。

高效调查围绕一个问题进行，例如：

- 用户运行哪个命令进入系统？
- 一段 WAV 如何变成识别文本？
- 配置和模型从哪里加载？
- 哪些测试保护这条路径？
- 修改某个函数会影响哪些调用者？

问题越具体，Codex 越容易选择正确的文件和证据。

## 2. 调查前先确认坐标

仓库调查至少要确认：

- 当前工作目录；
- 是否处于 Git 仓库；
- 当前分支或提交；
- 工作树是否已有改动；
- 有哪些生效的 `AGENTS.md` 或项目说明；
- 项目语言、运行环境和依赖管理方式。

你可以发送：

```text
先不要分析业务代码。确认当前工作目录、Git 根目录、分支、工作树状态、
项目语言与依赖管理方式，并列出生效的仓库说明文件。不要修改任何内容。
```

为什么要先做这一步？因为在错误目录得到的“正确分析”仍然没有用；忽略未提交改动则可能导致后续误删用户工作。

## 3. 五层漏斗调查法

### 第 1 层：项目契约

优先读取：

- `README.md`；
- `CONTRIBUTING.md`；
- `AGENTS.md`；
- 许可证和重要设计文档。

你想知道项目声称自己是什么、推荐入口是什么、如何验证。

### 第 2 层：构建与环境

常见文件包括 `pyproject.toml`、`package.json`、锁文件、Dockerfile、CI 配置。你想知道：

- 语言和最低版本；
- 依赖管理器；
- 测试、格式化、构建命令；
- 平台限制和外部服务。

本仓库的 `pyproject.toml` 明确要求 Python 3.13，并使用 `uv.lock` 锁定环境。这类结论应来自文件，而不是模型经验。

### 第 3 层：用户入口

从用户实际执行的命令、HTTP 路由、CLI `main()` 或公开 API 向内追踪。不要从一个看起来重要的内部文件随意开始。

在本项目中，`acoustic_engine/README.md` 列出最小命令；`acoustic_engine/recognize.py` 提供命令行入口；`acoustic_engine/engine.py` 封装识别契约。

### 第 4 层：核心调用链

沿具体数据流追踪：

```text
WAV 文件
→ load_mono_audio
→ LogMelFrontend
→ AcousticEngine.recognize_waveform
→ 声学模型 logits
→ greedy_decode / prefix_beam_search
→ RecognitionResult
```

这只是一张待验证的地图。每个箭头都要能对应到导入、函数调用、参数传递或测试。

### 第 5 层：测试与运行证据

测试告诉你维护者认为哪些行为重要，也能揭示边界条件和隐含契约。寻找：

- 与核心符号同名的测试；
- 正常路径、边界和错误路径；
- 集成测试如何构造对象；
- 测试命令是否真的可以运行。

本仓库的针对性命令是：

```powershell
uv run python -m unittest discover -s tests -p "test_acoustic_engine.py"
```

只阅读命令不能证明它通过。只有实际执行并记录退出码和结果，才能写“已运行通过”。

## 4. 搜索比猜文件名可靠

Codex 通常会使用快速文本搜索定位：

- 符号定义：`class AcousticEngine`；
- 调用者：`recognize_waveform(`；
- 错误字符串；
- CLI 参数；
- 测试名称；
- 配置键。

你不必背搜索命令，但要检查搜索问题是否合理。例如“找 `engine`”太宽；“找 `AcousticEngine.load` 的调用者和测试”更有方向。

## 5. 要求结论带证据等级

使用以下四类标签：

| 标签 | 含义 | 示例 |
|---|---|---|
| 已读取 | 文件内容直接支持 | `pyproject.toml` 要求 Python 3.13 |
| 已运行 | 命令或行为实际执行 | 指定测试共运行 N 项并通过 |
| 推断 | 多处线索共同指向但未运行 | 某入口可能是推荐部署路径 |
| 未确认 | 当前证据不足 | Windows 以外平台是否可用 |

提示词：

```text
每项架构结论都标注“已读取、已运行、推断、未确认”之一，并引用文件和符号。
不要把阅读到的示例命令写成已经执行。
```

## 6. 控制上下文噪音

不要把这些内容无差别灌入主聊天：

- 整个锁文件；
- 大型生成文件或模型权重；
- 所有测试日志；
- 所有 notebook 输出；
- 与问题无关的历史文档。

让 Codex先搜索，再读取相关片段；日志很长时，保留错误附近和总结。对后续决策重要的事实，要求写入项目文档或计划，不要只依赖聊天记忆。

## 7. 实战一：仓库鸟瞰图

新开聊天，发送：

```text
只读调查 G:\learn_asr，不要修改文件，也不要运行训练。

目标：为 Python 初学者建立一张可验证的项目鸟瞰图。
上下文：从 README.md、pyproject.toml、CONTRIBUTING.md、主要顶层目录和 tests/ 开始；
不要逐个读取 notebook 或模型产物。
约束：搜索后再选择文件；不联网；快速检查可以运行，但先说明目的。
完成标准：输出项目目标、环境要求、5–10 个关键目录、三个用户入口、
对应测试命令和风险提示。每项结论标注已读取/已运行/推断/未确认并给出证据位置。
```

审查问题：

1. 是否误把 46 个 notebook 全部总结了一遍？
2. 是否确认了 Python 版本和依赖工具？
3. 是否把“文档写了”误称为“运行通过”？
4. 关键入口能否对应到真实文件？

## 8. 实战二：追踪一条调用链

同一聊天继续：

```text
现在只追踪“WAV 文件到数字文本”的最短离线路径。
从 acoustic_engine/recognize.py 的用户入口开始，沿实际调用进入 engine.py、
features.py、model.py 和 decoder.py；同时找出直接保护该路径的测试。

输出：
1）按执行顺序编号的调用链；2）每步输入输出的 shape 或类型；
3）三个最容易改坏的契约；4）对应测试；5）仍未验证的环节。
引用具体符号，不修改文件，不运行模型训练。
```

如果 Codex 给出 shape，要检查是代码直接定义、测试断言还是推断。shape 错误在音频和机器学习项目中尤其常见。

## 9. 调查结束的好汇报

好的仓库调查不是“我读完了”，而是：

- 一张针对当前问题的最小地图；
- 可点击或可搜索的证据位置；
- 清楚区分事实和推断；
- 推荐的下一步调查；
- 明确指出没有调查的范围。

## 本课验收

不看教程，完成以下口试：

1. 五层漏斗分别是什么？
2. 为什么应从用户入口向内追踪？
3. “README 里有测试命令”属于哪种证据？
4. 为什么不应读取整个锁文件？
5. 如何验证一个调用链箭头不是猜测？

再提交一张 `WAV → 文本` 调用链地图。至少 8 个结论有具体文件或符号证据，且不存在把未运行命令冒充为已通过的情况，才算通过。
