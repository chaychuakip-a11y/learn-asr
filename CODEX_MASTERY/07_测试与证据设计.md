# 07：测试不是仪式，而是证据设计

## 本课目标

学会要求 Codex 设计能直接证明需求的测试，并判断“测试通过”究竟证明了什么、没有证明什么。

## 1. 从需求到证据

测试设计从用户可观察行为开始：

```text
需求
→ 必须保持的不变式
→ 可能失败的方式
→ 能区分正确与错误的输入
→ 可观察的断言
```

示例需求：“流式前端分块处理应与整段处理一致。”

- 不变式：相同波形和配置产生等价特征帧；
- 失败方式：chunk 边界丢样本、重复帧、最后残留未刷新；
- 输入：长度跨过多个帧且不能被 chunk 大小整除；
- 断言：帧数、shape、数值误差均满足约定；
- 相关现有测试：`test_streaming_frontend_matches_whole_waveform`。

这比“给 StreamingLogMelFrontend 写个测试”更能覆盖真实风险。

## 2. 测试金字塔

### 单元测试

隔离一个函数或类，速度快、定位准。例如 `ctc_collapse` 的 token 折叠规则。

### 集成测试

验证多个模块契约连接正确。例如前端输出能被模型和解码器消费。

### 端到端测试

从用户入口验证完整行为。例如调用 HTTP 接口上传 WAV 并检查响应契约。

越靠上越贴近用户，但通常越慢、越难定位。不要用一个巨大端到端测试替代所有单元测试，也不要只用单元测试证明完整服务可用。

## 3. 每项行为至少考虑三类输入

| 类别 | 问题 | 例子 |
|---|---|---|
| 正常路径 | 典型输入能否工作 | 标准 16 kHz 单声道音频 |
| 边界 | 临界值是否破坏不变式 | 空输入、单帧、chunk 末尾残留 |
| 错误路径 | 非法输入是否安全失败 | 错误采样率、损坏文件、非法 token |

必要时再增加：平台差异、并发、性能、随机性、兼容性和安全测试。

## 4. 回归测试的关键性质

一个强回归测试应该：

1. 在旧错误实现上失败；
2. 在修复后通过；
3. 失败原因与报告的 bug 相同；
4. 不依赖网络、时间、随机顺序等无关因素；
5. 断言用户或模块契约，而不是实现细节。

如果测试无论修不修都通过，它不能证明修复。如果测试只断言某个私有局部变量，它可能让未来安全重构变困难。

## 5. 精确性与容差

并非所有结果都应完全相等：

- token ID、长度、错误类型通常应精确相等；
- 浮点特征或模型 logits 可能使用有依据的误差容限；
- 性能指标需要多次测量、预热和稳定环境；
- 随机模型测试要固定种子，但仍要避免依赖脆弱的具体值。

容差必须来自数值性质或产品需求，不能为了让失败测试通过而随意扩大。

## 6. “测试绿了”仍可能证据不足

问以下问题：

1. 运行的是正确测试文件吗？
2. 测试是否真的被发现，还是运行了 0 项？
3. 新行为是否有直接断言？
4. 失败路径是否被跳过或 mock 掉？
5. 退出码是否为 0？
6. 只跑了针对性测试，还是也检查了相邻回归？
7. 环境是否与目标环境一致？

`Ran 0 tests ... OK` 不是成功证据。只看最后一个 `OK` 很危险。

## 7. 匹配范围的测试阶梯

变更后由窄到宽运行：

1. 新增或直接相关的单个测试；
2. 所在测试类或文件；
3. 相关模块测试；
4. 项目全量快速测试；
5. 需要时才运行耗时训练、外部数据或部署验证。

这样能快速反馈，又不会把“全量太慢”当成不测试的借口。昂贵验证若未运行，应明确写入风险，而不是暗示已覆盖。

本项目的核心声学引擎测试可用：

```powershell
uv run python -m unittest discover -s tests -p "test_acoustic_engine.py"
```

运行单项测试时使用完整测试路径，并先确认路径真的能被 `unittest` 发现。

## 8. 让 Codex先写测试计划

对中等以上改动先要求：

```text
先不要写代码。把需求拆成可观察行为和不变式，列出正常、边界、错误路径。
检查现有测试风格和夹具，提出最小测试集合。
对每个测试说明：它证明什么、修复前为何应失败、仍不能证明什么、预计运行成本。
```

然后你裁决：是否遗漏真正的用户行为？是否为了容易测试而测试了错误的层？

## 9. Mock 的边界

Mock 可以隔离昂贵或不稳定依赖，但过度 mock 会让测试只证明“你预设的模拟会按预设工作”。

适合 mock：

- 外部网络；
- 时间、随机或付费服务；
- 极慢模型；
- 明确的模块边界。

不应轻易 mock：

- 正在验证的核心逻辑；
- 你怀疑契约不匹配的两个模块之间；
- 实际序列化、文件格式或框架行为，而这些正是风险来源。

## 10. 实战：审计现有测试覆盖

发送：

```text
只读审计 acoustic_engine/decoder.py 与 tests/test_acoustic_engine.py 中的 DecoderTests，
不要修改文件。

目标：建立 decoder 公开行为与测试之间的映射。
约束：不运行训练，不联网；允许执行现有的快速 DecoderTests。
完成标准：
1）列出 ctc_collapse、greedy_decode、StreamingGreedyDecoder、prefix_beam_search
的关键不变式；2）映射已有测试；3）指出证据充分、部分覆盖和未覆盖项；
4）为最高价值缺口设计一个最小测试，但先不实现；
5）说明该测试证明什么和不能证明什么。
```

不要接受仅凭“函数有测试”就写“覆盖充分”。一个函数可能有很多独立行为。

## 11. 实战：实现一个高价值测试

从审计中选择一项已证实缺口，再发送：

```text
实现刚才选定的一个测试。先确认它不与现有测试重复，并沿用 unittest 风格。
如果测试暴露真实失败，先停在失败证据并报告，不要自动修改生产代码；
如果当前实现已经通过，解释该测试防止的未来回归。
运行该测试、DecoderTests 和 test_acoustic_engine.py，记录测试数量、退出码和结果。
最后审查 diff，确保没有模型训练、数据或产物变化。
```

这里特意不自动授权修复：你要练习区分“补测试”和“改行为”是两个不同任务。

## 12. 测试报告模板

```text
需求/风险：
测试层级：单元 / 集成 / 端到端
输入类别：正常 / 边界 / 错误
修复前结果：
修复后结果：
直接证明：
没有证明：
执行命令、测试数量、退出码：
不稳定性或环境限制：
```

## 本课验收

提交一个测试设计并回答：

1. 为什么它在错误实现上会失败？
2. 它断言的是外部契约还是偶然实现细节？
3. 是否真的被测试运行器发现？
4. 它覆盖什么输入类别？
5. 还需要哪一层测试才能证明完整用户行为？

必须实际运行至少一个针对性测试，并准确报告测试数量和退出码。不能用“全部通过”代替这些信息。
