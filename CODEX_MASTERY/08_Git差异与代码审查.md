# 08：Git、差异审查与安全回退

## 本课目标

你不需要先成为 Git 专家，但必须能回答三个问题：当前发生了什么变化、哪些变化属于本任务、怎样安全地接受或撤销它们。

## 1. Git 的最小心智模型

```text
历史提交（HEAD）
       ↓
暂存区（准备进入下一次提交）
       ↓
工作树（你当前看到的文件）
```

一个文件可以同时存在暂存和未暂存变化。Codex 的 review 面板反映 Git 仓库状态，其中可能同时包含你、Codex 和其他工具产生的改动，不能假设所有变化都是“上一轮 Codex 改的”。

## 2. 任务开始前的基线

要求 Codex先检查：

- 当前分支；
- `git status --short`；
- 是否有未跟踪文件；
- 与任务重叠的已有修改；
- 是否需要在独立工作树或分支中处理。

基线不是为了强制工作树干净，而是为了保护已有工作。仓库脏并不等于必须清理；未经允许不得覆盖或丢弃陌生改动。

## 3. 常用状态含义

你可能在简短状态中看到：

| 标记 | 大意 | 你的问题 |
|---|---|---|
| `??` | 未跟踪文件 | 是本任务新建，还是用户已有？ |
| ` M` | 工作树中已修改 | 是否与当前任务有关？ |
| `M ` | 已暂存修改 | 谁准备提交，是否应保持？ |
| `MM` | 暂存后又继续修改 | 两部分分别是什么？ |
| `D` | 删除 | 删除是否明确授权且可恢复？ |

不要求死记所有代码；遇到不懂时让 Codex解释当前具体状态，不要猜。

## 4. 三种最重要的 diff

- 工作树相对暂存区：当前未暂存变化；
- 暂存区相对 HEAD：准备提交的变化；
- 分支相对基线：整个功能分支变化。

审查前先说明范围。只看“最后一轮”可能漏掉早先改动；看整个未提交区又可能混入用户工作。

官方 Codex `/review` 支持审查基线分支、未提交变化或指定提交，并以只读方式输出优先级化发现。它默认不会修改工作树；之后如果要求应用修复，才进入正常写入和权限流程。

## 5. Diff 审查的两遍法

### 第一遍：范围与意图

只问：

- 修改文件是否符合任务预期？
- 有没有大量格式化、重命名或生成产物？
- 删除是否有理由？
- 是否混入另一个目标？

### 第二遍：行为与风险

逐个变更问：

- 正常、边界、错误路径会怎样？
- 接口、数据格式、兼容性是否变化？
- 错误是否被隐藏？
- 新行为有没有测试？
- 测试是否能在旧错误上失败？
- 文档和实现是否同步？

两遍分开能避免一开始陷入代码细节而漏掉巨大范围问题。

## 6. 好的代码审查发现长什么样

每项 finding 应包含：

1. 严重度：例如高、中、低；
2. 精确位置：文件和尽量小的行范围或符号；
3. 触发条件：什么输入、环境或顺序会发生；
4. 错误行为：用户或系统会看到什么；
5. 原因：为什么当前变更导致它；
6. 修复方向：可选，且不掩盖 finding 本身。

弱发现：“这里可能有性能问题。”

强发现：

```text
[中] engine.py / recognize_waveform：每次请求都重建同一 Mel filterbank。
当 HTTP 服务连续处理请求时，配置不变但该张量仍重复分配，延迟随请求数累积。
现有构造函数已经持有 frontend，可将不可变 filterbank 缓存在 frontend 实例中。
需要基准确认实际影响；当前属于代码路径证据，尚无性能测量。
```

强发现也必须诚实区分“代码上可见”与“已经测量”。

## 7. 严重度如何判断

可采用：

- 高：数据损坏、安全漏洞、广泛崩溃、无法安全发布；
- 中：常见场景错误、明显兼容回归、重要测试空洞；
- 低：有限边界错误、可维护性风险、文档偏差；
- 建议：非错误的改进想法，不应冒充阻塞问题。

严重度取决于发生概率和影响，不取决于代码看起来复杂不复杂。

## 8. 审查提示词

```text
只读审查当前未提交变化，不要修改。

先确认审查范围并区分用户原有改动与本任务改动。根据原始需求逐项检查，
优先发现会导致错误行为、数据损坏、安全问题、兼容性回归或关键测试缺失的问题。
每项给严重度、精确文件/符号、触发条件、错误结果和理由。
不要把纯风格偏好列为 bug；不要重复同一根因。
如果没有发现，明确说“未发现具体问题”，并列出没有运行或无法覆盖的验证。
```

如果只想聚焦：

```text
/review
重点检查音频 shape/length 契约、流式 chunk 边界状态、错误采样率处理和回归测试。
```

不同 Codex 界面可用的具体 review 选项可能不同；以当前界面和官方文档为准。

## 9. 如何裁决审查发现

Codex 的 finding 不是判决。逐项分类：

- 接受：证据成立，需要修；
- 拒绝：与规格或代码事实不符，记录理由；
- 需要验证：机制合理但缺少复现；
- 延后：成立但超出当前目标，创建明确后续项；
- 重复：与另一项同根因。

对“可能”“也许”类 finding，先要求最小复现或具体调用路径。不要让 Codex为了处理 review 而无止境扩大范围。

## 10. 安全回退原则

回退之前必须知道精确目标。危险做法包括：

- 对整个仓库执行破坏性重置；
- 因为测试生成了文件就批量删除未知目录；
- 用旧版本覆盖同时包含用户改动的文件；
- 不区分 staged 和 unstaged 就全部丢弃。

优先策略：

1. 只回退本任务明确产生的最小 hunk 或文件；
2. 先保存 diff 或提交检查点；
3. 对同时含用户改动的文件，手工合并或询问；
4. 删除物质性文件后说明目标和可恢复性。

你可以要求：

```text
先不要执行回退。列出你本次产生的精确文件和 hunk，说明其中是否混有用户已有改动，
并提出最小、可恢复的回退方案。任何会丢弃未提交工作的命令都等我确认。
```

## 11. 提交不是默认授权

“实现并验证”通常不自动等于“提交、推送、创建 PR”。这些动作改变协作状态，应由任务明确授权。

提交前检查：

- diff 只包含一个连贯目标；
- 测试和验证结果已记录；
- 没有密钥、个人路径、缓存或大产物；
- 提交说明描述结果和原因；
- 未把用户无关改动一起提交。

推送、创建 PR、合并和发布比本地提交影响更大，需要更明确的目标与确认。

## 12. 实战一：审查阶段 B 教程变化

当前 `CODEX_MASTERY/` 是未跟踪目录，很适合学习“未跟踪不等于不存在”。让 Codex：

```text
只读审查 CODEX_MASTERY/ 当前变化，不要编辑、暂存或提交。
先解释 git status 为什么把整个目录显示为 ??，以及仅看普通 git diff 为什么可能看不到内容。
然后审查 05–08 章节是否满足：面向只会提问和 compact 的初学者、
每章有概念/示例/实战/验收、命令适配 Windows PowerShell、内部链接有效。
发现按严重度报告；纯文风建议单独列出，不冒充错误。
```

这个练习让你看到：Git 状态和 diff 范围选择本身就是证据链的一部分。

## 13. 实战二：独立审查一次代码改动

选择第 07 课产生的测试改动：

1. 原实现聊天保存原始任务和验证结果；
2. 新开聊天或使用 `/review` 审查未提交变化；
3. 审查者只得到需求、diff 和测试约束，不提供实现者的自我辩护；
4. 对每项 finding 进行接受、拒绝、验证或延后；
5. 需要修复时回到实现聊天或明确授权审查聊天修改；
6. 修改后重新运行验证和 review。

独立审查可以降低实现者对自己方案的确认偏误，但仍不能代替实际测试。

## 14. 阶段 B 综合验收

提交一个真实、小范围改动，并提供：

- 仓库坐标和改动前 Git 基线；
- 相关调用链和现有测试地图；
- bug 或需求的可验证规格；
- 修复前证据（适用时）；
- 实现 diff；
- 针对性与相邻测试命令、测试数量、退出码；
- 独立 review findings 及逐项裁决；
- 最终 Git 状态和未验证风险；
- 如果需要回退，精确回退方案。

## 评分表

每项 0–2 分，共 20 分：

| 项目 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 仓库坐标 | 未确认 | 只确认目录 | 分支、状态、说明和环境均确认 |
| 调用链 | 猜测 | 有文件清单 | 按入口追踪且箭头有证据 |
| 诊断 | 直接改 | 单一假设 | 稳定复现并排除替代假设 |
| 根因 | 只报症状 | 接近错误点 | 找到最早错误状态 |
| 测试设计 | 无 | 只测正常路径 | 覆盖关键不变式和风险 |
| 测试执行 | 未运行 | 模糊说通过 | 命令、数量、退出码完整 |
| diff 范围 | 未检查 | 看了文件名 | 区分来源并检查意外变化 |
| review | 无 | 泛泛建议 | 发现可触发、定位准确、分级合理 |
| finding 裁决 | 全盘接受 | 有少量判断 | 逐项以证据接受或拒绝 |
| 恢复与风险 | 无 | 笼统可回退 | 精确回退且诚实记录证明缺口 |

达到 16 分，且“诊断、测试执行、diff 范围、review”均不为 0，阶段 B 通过。
