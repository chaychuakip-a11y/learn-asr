# 14：配置、模型、推理强度、权限与沙箱

## 本课目标

Codex 的表现不仅由提示词决定，还受到配置、模型、推理强度、工作目录、沙箱和批准策略影响。本课让你学会按任务风险选择最小权限，并避免通过“全放开”掩盖环境问题。

## 1. 配置与指令不是一回事

| 层 | 负责什么 | 例子 |
|---|---|---|
| 提示词 | 本次任务目标和边界 | 只修这个 bug，不改 API |
| `AGENTS.md` | 仓库长期工作约定 | 使用 `uv`，运行指定测试 |
| `config.toml` | Codex 运行参数和工具环境 | 默认模型、沙箱、MCP、功能开关 |
| `requirements.toml` | 组织管理员强制限制 | 禁止 full access 或 never approval |
| CI/Hook | 机械执行和验证 | 每次变更自动测试 |

不要把“使用哪个模型”写进项目 README，也不要用配置文件表达一次性业务需求。

## 2. 配置作用域与优先级

常见层级：

1. 一次性 CLI flags/配置覆盖；
2. 可信项目中的 `.codex/config.toml`，越靠近当前目录越优先；
3. 选中的 profile 配置；
4. 用户级 `~/.codex/config.toml`；
5. 系统配置；
6. 内置默认值。

项目未被信任时，项目级 `.codex/` 配置、hooks 和 rules 可能不加载。这是安全边界，不应通过盲目复制到用户全局配置绕过。

## 3. 最小配置示例

```toml
# ~/.codex/config.toml
model = "gpt-5.6"
model_reasoning_effort = "medium"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
web_search = "cached"

[windows]
sandbox = "elevated"
```

这是结构示例，不是所有账户和环境的强制推荐。模型可用性、组织策略和界面选项会变化；修改前查看当前官方文档和实际可选项。

Windows 的 `elevated` 指官方推荐的原生沙箱实现设置，不等于给所有命令无限管理员权限。不要从名称直接推断实际权限范围。

## 4. 模型与推理强度如何选

从任务出发，而不是迷信“永远选最大”：

| 任务 | 起点 | 何时提高推理强度 |
|---|---|---|
| 格式或明确小改 | 默认/较低 | 出现隐藏约束或跨文件影响 |
| 读仓库、普通实现 | 默认/中等 | 调用链复杂、测试不明确 |
| 根因诊断、架构迁移 | 中高 | 多假设、风险高、需长计划 |
| 独立审查、安全分析 | 中高 | 需要跨模块和攻击路径推理 |

更高推理强度通常更慢、消耗更多。它不能替代正确上下文、复现、测试或权限。

做模型选择时记录：

- 任务类型；
- 成功标准；
- 质量、延迟和成本偏好；
- 是否需要工具、图像或长上下文；
- 实际结果，而不是主观印象。

## 5. 沙箱和批准策略的区别

- 沙箱：命令实际能访问哪些文件、网络和系统资源。
- 批准策略：什么情况下 Codex 要暂停并询问你。

一个动作即使“不询问”，仍可能被沙箱阻止；一个动作即使沙箱允许，也可能按策略要求批准。两者是不同控制层。

## 6. 常见权限级别的直觉

### Read only

适合解释、调查、审查和计划。不能依赖写文件或安装依赖完成任务。

### Workspace write

适合大多数受信任仓库内的编码任务。允许在工作区修改，但网络和工作区外访问通常更受限。

### Full/danger access

适合隔离、受控环境中确实需要广泛系统访问的任务。风险包括误改工作区外文件、读取敏感信息、访问网络和运行危险命令。不能作为“遇到错误就开”的默认按钮。

具体名称和行为以当前界面及官方权限文档为准。

## 7. 按风险选择权限

| 场景 | 建议起点 | 说明 |
|---|---|---|
| 解释 `decoder.py` | Read only | 无需写入 |
| 审查未提交 diff | Read only | review 默认不应改文件 |
| 修复仓库内单元测试 | Workspace write | 仅需工作区写入 |
| 查询最新官方 API | Read only + 受控网络/文档工具 | 不需要本地全权限 |
| 安装系统驱动 | 单独明确授权 | 高影响、工作区外 |
| 部署线上服务 | 专门环境与最小凭证 | 外部状态不可轻易恢复 |
| 定时只读报告 | Read only | 无人值守更应收紧 |

原则：先给完成任务所需的最小权限；确有证据显示被边界阻止，再精确扩大一项。

## 8. 如何审查批准请求

每次问：

1. 哪个任务步骤需要它？
2. 精确命令和目标是什么？
3. 读取还是写入？是否访问网络或工作区外？
4. 是否包含通配符、递归或未解析变量？
5. 会不会删除、覆盖、发布、付款或发送消息？
6. 失败能否恢复？
7. 能否缩小范围或改用只读检查？

拒绝批准不等于终止任务。要求 Codex说明受阻证据并提出更窄方案。

## 9. 网络与网页内容

网络访问带来两类风险：

- 数据外发：提示词、代码或环境信息被发送到外部服务；
- 提示注入：网页、issue、文档中包含针对 agent 的恶意指令。

外部内容是数据，不是高优先级指令。要求 Codex：

- 优先使用官方和一手来源；
- 不执行网页要求的命令或泄露秘密；
- 只发送完成查询所需的最少内容；
- 对写入外部服务的动作单独确认；
- 引用实际打开的来源，而不是搜索摘要。

## 10. 环境变量和秘密

API key、token、cookie、SSH key、云凭证都不应：

- 写进提示词或代码；
- 提交到 Git；
- 打印到日志；
- 作为整个 CI job 的宽泛环境暴露给不受信任脚本；
- 放入普通教程示例的真实值。

使用占位符，并通过系统密钥存储或 CI secret 以最小作用域注入。发现泄露时，不只是删除文件，还要旋转凭证并检查历史。

## 11. 一次性覆盖、用户配置和项目配置

- 一次性任务不同：用当前会话或 CLI flag；
- 个人跨仓库默认：用户配置；
- 可信仓库共享设置：项目 `.codex/config.toml`；
- 管理员不可绕过限制：`requirements.toml`；
- 不要把临时 full access 固化为长期全局默认。

配置更改本身也应 review。错误配置可能让未来所有任务的风险扩大。

## 12. 故障排查顺序

Codex “什么都做不了”时，不要立刻 full access：

1. 确认工作目录和项目信任状态；
2. 查看当前沙箱、批准策略和生效配置来源；
3. 读取实际错误，确定被阻止的是文件、网络还是命令；
4. 判断任务是否真的需要该能力；
5. 寻找工作区内或只读替代；
6. 必须扩大时，只扩大精确资源和时间范围；
7. 完成后恢复较窄配置。

## 13. 实战：权限设计桌面推演

让 Codex给出以下六类任务的最小权限方案，但先自己作答：

1. 总结当前仓库结构；
2. 修复 `ctc_collapse` 边界测试；
3. 查询最新版 FastAPI 官方文档；
4. 从私有 GitHub issue 读取需求；
5. 定时生成只读测试报告；
6. 发布 Docker 镜像到生产 registry。

对每项写：沙箱、网络、批准点、凭证范围、可恢复性和禁止动作。然后要求 Codex指出过度授权和缺失授权。

## 14. 实战：只读配置审计

```text
只读审计当前 Codex 会话与 G:\learn_asr 的配置边界，不要修改任何配置。

目标：说明用户级、项目级、会话级和管理员约束中哪些实际可见、哪些无法确认。
输出当前工作目录、项目信任、生效的沙箱/批准模式、相关配置来源、
项目 AGENTS 与 config 的区别，以及完成“只读审查”和“仓库内修复”各自所需最小权限。
不要读取或输出密钥值；无法验证的设置明确写未知。
```

不要要求 Codex把所有全局配置全文打印，因为其中可能包含敏感服务器、路径或环境信息。

## 本课验收

你应能对 6 个场景独立选出最小权限，并解释：

1. 沙箱与批准策略有什么区别？
2. 配置优先级如何工作？
3. 项目不受信任时会发生什么？
4. 为什么更高推理强度不能替代测试？
5. 遇到权限错误为什么不应直接 full access？

至少识别一个自己原本会过度授权的场景，并写出更窄替代方案，才算通过。
