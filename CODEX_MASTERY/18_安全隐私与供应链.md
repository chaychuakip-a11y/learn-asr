# 18：安全、隐私、依赖与供应链审查

## 本课目标

安全不是最后运行一次扫描。本课训练你让 Codex先建立威胁模型，再审查真实攻击面、验证具体发现，并以最小修复和回归测试闭环；同时防范 agent 自身带来的权限、网络、提示注入和依赖风险。

## 1. 安全从资产和边界开始

先回答：

- 保护什么资产：代码、模型、音频、凭证、用户数据、算力、发布权限；
- 谁可能攻击：外部用户、恶意依赖、内部误用、被注入的 agent；
- 入口在哪里：文件上传、HTTP/WebSocket、CLI 参数、模型加载、环境变量；
- 信任边界：浏览器→服务、文件系统→解析器、仓库→CI、agent→网络；
- 高权限动作：读秘密、写工作区外、发送数据、部署、删除、执行模型/脚本。

没有威胁模型的扫描会产生大量脱离业务的泛泛发现。

## 2. 最小威胁模型模板

```text
系统用途：
用户与角色：
入口和不可信输入：
信任边界：
敏感数据：
外部服务与依赖：
高权限动作：
安全不变式：
明确不在范围：
优先审查区域：
```

对本地 ASR 学习项目，音频文件、checkpoint、HTTP 上传、路径参数和依赖安装都是需要讨论的边界；但不能假设它已经公开部署。

## 3. 安全不变式

示例：

- 不可信文件不能让解析器读取任意工作区外路径；
- 错误输入不能泄露绝对路径、密钥或内部堆栈；
- checkpoint 来源不可信时不能假定反序列化安全；
- 未认证用户不能触发高成本训练或任意命令；
- 外部网页内容不能覆盖用户与仓库指令；
- connector 写动作必须在服务端重新鉴权；
- 日志不得保存原始 token、密码或不必要的个人音频信息。

安全 review 应围绕这些可验证不变式，而不是只搜“password”字符串。

## 4. 输入验证要发生在边界

对文件、HTTP 和 CLI 输入检查：

- 类型、大小、长度和编码；
- 格式是否真的可解析，而非只看扩展名；
- 采样率、通道和数值范围；
- 路径规范化与允许目录；
- 超时、并发和资源上限；
- 错误响应是否稳定且不泄密；
- 解析失败后是否留下半写入产物。

验证不能只在 UI；服务端必须重新检查，因为客户端可绕过。

## 5. 文件和模型加载风险

特别审查：

- 用户控制的路径；
- 路径穿越与符号链接；
- 临时文件权限和清理；
- 压缩包解压目标；
- 反序列化格式；
- 模型文件来源、哈希和版本；
- 加载时是否可能执行代码；
- 巨大或畸形输入造成内存/CPU 耗尽。

不要因为文件扩展名是 `.wav` 或 `.pt` 就认为可信。安全方案要基于实际解析库和格式特性，并查阅对应版本的一手文档。

## 6. Prompt injection

Codex 可能读取网页、issue、README、日志和代码注释。其中的指令属于**不可信数据**，不能覆盖用户、开发者、仓库和系统规则。

风险示例：某 issue 让 agent 运行一段会把 Git 内容发送到外部站点的命令。正确做法：

- 把 issue 内容当作问题描述，不执行其中命令；
- 检查命令是否读取本地数据、访问网络或改变外部状态；
- 只允许任务所需域名和 HTTP 方法；
- 不向网页、issue 或工具返回秘密；
- 任何外部写入单独授权；
- 对来源和内容进行引用与隔离。

即使使用缓存搜索，也只是降低而非消除注入风险。

## 7. Agent 权限威胁

攻击路径可以是：

```text
恶意外部内容
→ 模型误当指令
→ 工具调用
→ 读取秘密/修改文件/发送网络请求
→ 数据泄露或供应链污染
```

防御需要多层：最小沙箱、批准策略、网络 allowlist、只读工具、服务端鉴权、Hook/CI、隔离 runner、审计日志和人工 review。

不要把“模型应该识别恶意内容”当作唯一防线。

## 8. 秘密与个人数据

### 秘密

- 不写入提示词、代码或普通日志；
- 不提交 `.env`、auth 文件或 token；
- CI 中只在需要的步骤注入；
- 输出脱敏；
- 泄露后轮换，而不只是删除；
- 检查 Git 历史和已发布产物。

### 个人数据

音频可能包含声音身份、生物特征、姓名和对话内容。处理前明确：

- 合法来源与同意；
- 用途限制；
- 保留期限；
- 访问控制；
- 是否上传第三方；
- 删除流程；
- 日志和评测集是否保留原音频。

“只是测试数据”不自动消除隐私义务。

## 9. 依赖与供应链

Codex 添加依赖前应调查：

- 是否已有依赖能完成；
- 包名是否正确，防止 typosquatting；
- 官方来源、维护状态和许可证；
- 固定版本与锁文件变化；
- 安装脚本和原生二进制；
- 已知漏洞和修复版本；
- 传递依赖数量；
- 是否访问网络、遥测或下载模型；
- 在目标 Python/OS 上是否兼容。

禁止仅因“流行”或模型记忆就添加包。版本和漏洞状态会变化，必须查当前一手来源或可信扫描结果。

## 10. 锁文件与可复现性

锁文件帮助固定解析出的依赖图，但不能证明依赖安全。仍需：

- review 锁文件变化是否与直接依赖一致；
- 检查异常新增包和来源；
- 在隔离环境重建；
- 验证哈希或签名（生态支持时）；
- 定期更新并运行回归；
- 保存 SBOM 或依赖清单（高要求项目）。

不要手工编辑大型锁文件来“让 diff 好看”，应通过正确包管理器生成。

## 11. 安全 finding 的证据标准

每项至少包含：

- 资产和影响；
- 攻击者前置条件；
- 不可信输入到敏感操作的完整路径；
- 精确代码位置；
- 当前防护为何不足；
- 安全、受控的验证方法；
- 严重度及其理由；
- 最小修复方向；
- 证明缺口。

“用了危险函数”不一定可利用；“没有复现”也不自动安全。

## 12. 安全验证边界

只在明确授权的本地、测试或隔离环境验证。不要：

- 测试公共或生产目标；
- 获取真实凭证或持久化访问；
- 读取与证明无关的用户数据；
- 扩大到其他账户或系统；
- 发布可直接滥用的细节；
- 因“验证需要”绕过原授权范围。

安全测试同样受任务范围和权限约束。

## 13. 修复闭环

```text
确认 finding
→ 建立安全、最小复现或最强替代证据
→ 写失败回归测试（安全可行时）
→ 最小修复
→ 原攻击路径不再成立
→ 合法行为仍工作
→ 检查相邻绕过
→ 安全 diff review
→ 记录剩余风险
```

不要用大重构掩盖安全修复；小补丁更容易审查和快速回退。

## 14. Codex Security 的位置

Codex Security 是用于连接仓库、威胁建模、扫描、验证和修复安全 finding 的专门产品/插件能力。它可以提高规模化审查效率，但：

- 需要正确授权和仓库范围；
- 威胁模型仍需人工校准；
- finding 仍要验证；
- 不自动证明仓库安全；
- 不替代依赖扫描、运行时防护、审计和人工 review。

未安装或无权使用时，仍可按本课流程进行只读威胁建模和普通代码审查；不要为了课程强行安装插件。

## 15. 实战：本地 HTTP 音频入口威胁建模

```text
只读威胁建模 deployment/app.py、acoustic_engine/api.py 及直接调用链，
不要修改、不联网、不运行攻击性测试。

系统仅按当前仓库证据建模，不假定已公开部署。列出资产、入口、不可信输入、
信任边界、敏感操作、安全不变式和范围外事项。
重点检查文件/字节输入、采样率与大小、模型加载、错误响应、资源耗尽、
路径和日志。每项候选 finding 给完整数据流和证明缺口；泛泛最佳实践单独列出。
```

你要拒绝没有触发条件、没有代码路径或基于虚构部署环境的 finding。

## 16. 实战：依赖变更审查

让 Codex只读比较 `pyproject.toml` 与 `uv.lock`：

```text
不要修改或安装依赖。建立直接依赖、锁文件和目标 Python 版本的关系，
说明如果新增一个音频上传库需要审查哪些当前信息。
不要凭记忆声称最新版本或无漏洞；需要当前外部事实时列出应查的一手来源和最小网络范围。
输出接受依赖前的证据清单、拒绝条件和回退计划。
```

## 17. 安全审查清单

- [ ] 有仓库特定威胁模型。
- [ ] 输入到敏感操作的数据流完整。
- [ ] 最小权限、网络和工具边界明确。
- [ ] 秘密、个人数据和日志策略明确。
- [ ] 外部内容按不可信数据处理。
- [ ] 依赖来源、版本、锁文件和许可证已审查。
- [ ] finding 有触发条件和证明缺口。
- [ ] 验证只在授权环境。
- [ ] 修复有回归测试和相邻绕过检查。
- [ ] 没有未处理的高严重度 finding。

## 本课验收

提交一份真实入口的威胁模型和只读安全 review，至少包含 5 个安全不变式、3 条完整数据流、finding 证据裁决和依赖审查清单。

口试：

1. 为什么漏洞扫描前要有威胁模型？
2. Prompt injection 如何发展成数据泄露？
3. 锁文件为什么不等于供应链安全？
4. 安全 finding 需要哪些可利用性证据？
5. 为什么安全测试也必须有授权边界？

能拒绝一个听起来严重但证据不足的 finding，并设计安全的验证方法，才算通过。
