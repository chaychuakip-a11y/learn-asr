# 12：多 agent 协作与并行边界

## 本课目标

多 agent 不是“越多越强”。每个 agent 都消耗上下文、工具时间和 token，并带来协调成本。本课训练你识别真正可并行的任务，写出清晰委派契约，并由主 agent 对最终结果负责。

## 1. 主 agent 与 subagent

- 主 agent：持有原始目标、用户决策、总计划和最终整合责任。
- subagent：接受一个具体、有边界的子任务，在自己的 agent thread 中工作并返回结果。
- agent thread：子 agent 的独立对话与工作记录，可用于检查进度和结果。

多 agent 可以减少主聊天的日志噪音，让探索、测试或资料核对在独立上下文中进行。它不能自动解决错误拆分、共享文件冲突或模糊完成标准。

## 2. 什么任务适合并行

优先选择彼此独立、读多写少的任务：

- 一个 agent 映射调用链；
- 一个 agent 审计测试缺口；
- 一个 agent 检查文档与实现一致性；
- 一个 agent 分析日志或性能数据；
- 多个 agent 分别审查安全、正确性、兼容性；
- 独立资料来源的核对。

适合并行的数学直觉：

```text
并行收益 > 启动成本 + 重复调查 + 汇总成本 + 冲突风险
```

一个五分钟能完成的单文件修改，通常不值得启动四个 agent。

## 3. 不适合直接并行的任务

- 多个 agent 同时修改同一文件；
- 子任务强依赖前一个结果；
- 需求尚未澄清；
- 所有人都要先读取相同大量上下文；
- 修改共享数据库、端口或外部服务；
- 最终接口需要频繁协商；
- 只有一个不可并发资源，例如单 GPU 训练。

这类工作应串行，或先把接口和文件所有权切清楚，再使用独立 worktree。

## 4. 委派契约的六要素

每个子任务写清：

1. 目标：要回答或产出什么；
2. 范围：读哪些文件、不要碰哪里；
3. 权限：只读还是允许写；
4. 证据：结论需怎样证明；
5. 输出：主 agent 需要什么格式；
6. 完成/停止：何时返回，遇到什么不要自行扩大范围。

示例：

```text
启动一个只读 subagent 审计 acoustic_engine/decoder.py 的测试覆盖。
范围仅限 decoder.py、tests/test_acoustic_engine.py 和必要调用者；不修改、不训练、不联网。
输出行为→测试映射、最高价值的三个缺口、文件/符号证据和未确认项。
如果判断缺口需要产品规格，不自行决定行为，返回决策问题。
```

“找个人看看测试”没有范围、证据或停止条件，极易漂移。

## 5. 如何拆分而不重复

### 按关注点拆分

- 正确性；
- 安全；
- 性能；
- 测试；
- 文档。

适合代码审查，但不同 agent 仍可能发现同一根因，主 agent 要去重。

### 按组件拆分

- 前端；
- 模型；
- 解码；
- 服务。

适合边界清晰的仓库调查，但跨组件契约必须由主 agent 统一检查。

### 按阶段拆分

调查→实现→测试→审查通常是依赖链，不应全部同时启动。可以让调查 agent 和资料 agent 并行，汇总后再启动实现，完成后再独立 review。

## 6. 读并行、写串行是安全起点

初学者推荐：

```text
并行只读调查
→ 主 agent 汇总并做决策
→ 一个明确所有者实施修改
→ 独立 subagent 审查
→ 主 agent 裁决并验证
```

这能获得多视角，同时避免多个 agent 写同一工作树。

如果确实需要并行写入：

- 使用独立 worktree/分支；
- 每个 agent 拥有互不重叠的文件或组件；
- 先固定接口；
- 明确整合所有者；
- 合并后运行跨组件测试；
- 不假设“各自测试通过”就代表集成成功。

## 7. 权限不会因分工而消失

subagent 继承父任务的沙箱和权限环境。批准请求可能来自你当前没有查看的 agent thread。批准前确认：

- 是哪个 agent；
- 它的委派目标是否需要该动作；
- 精确命令和目标；
- 是否越过只读范围；
- 是否会影响共享外部状态。

给 subagent 配置只读并不能让所有外部风险自动消失；仍要检查可用工具和任务范围。

## 8. 主 agent 的汇总责任

主 agent不能简单拼接四份报告。它需要：

1. 检查每个子任务是否按范围完成；
2. 区分证据、推断和未确认；
3. 处理互相矛盾的结论；
4. 合并同根因发现；
5. 判断跨组件影响；
6. 对照原始目标检查遗漏；
7. 决定下一步，而不是让多数票决定事实。

汇总模板：

```text
子任务与状态：
一致结论及共同证据：
冲突结论及各自证据：
重复发现合并：
跨组件风险：
尚未覆盖：
主 agent 裁决：
对原始目标的影响：
```

## 9. 冲突处理协议

两个 agent 结论冲突时：

1. 不按模型语气或多数票裁决；
2. 找出它们使用的代码版本和假设是否相同；
3. 要求双方提供最小证据位置；
4. 设计一个能区分两种解释的实验；
5. 必要时由第三个只读 agent 独立裁决；
6. 最终由主 agent结合实际运行结果决定。

## 10. 监控和纠偏

在支持的 Codex 客户端中，可查看 subagent 状态；CLI 可使用 `/agent` 或 `/subagents` 切换 agent thread。

需要纠偏时，发送具体信息：

```text
停止继续扫描 notebook；这超出委派范围。只完成 decoder.py 的行为→测试映射，
保留已找到的文件证据并在 10 项以内返回。
```

何时应停止 agent：

- 子任务已被另一个结果取代；
- 明显偏离范围；
- 持续重复无信息增益的动作；
- 即将执行未授权外部操作；
- 继续成本高于预期价值。

## 11. 常见失败模式

### 复制粘贴式并行

给所有 agent 同一个宽泛任务，得到四份高度重复报告。

### 过早并行

规格未定就让多个 agent分别实现，最后接口互不兼容。

### 共享写冲突

多个 agent同时格式化或编辑同一文件，覆盖彼此和用户改动。

### 汇总丢证据

主 agent只说“大家一致认为”，却不保留文件位置和测试结果。

### 子任务完成冒充总目标完成

三个调查都完成，不等于功能已经实现和验证。

### 成本失控

小任务启动大量高推理 agent，花费和等待远高于单 agent。

## 12. 第一次多 agent 练习：只读三视角审计

这次练习需要你**明确要求 Codex 使用 subagents**；若当前客户端或账户不支持，就用三个独立聊天模拟，方法仍然成立。

提示词：

```text
对 CODEX_MASTERY 的阶段 A–C 做一次并行、只读审计。请显式启动三个有界 subagent：

1. beginner_reviewer：检查是否适合只会提问和 compact 的初学者，找术语跳跃。
2. exercise_reviewer：检查每章练习能否在 G:\learn_asr 安全执行，命令和证据是否具体。
3. curriculum_reviewer：对照完整教学大纲，检查 01–12 的能力覆盖、重复和缺口。

所有 agent 只读，不编辑、不联网、不运行训练；每个最多返回 5 项高价值发现，
每项引用文件和章节。等待三者完成后，由主 agent去重、处理冲突，
按高/中/低分级，并给出“立即修、后续修、拒绝”建议。不要自动修改。
```

你要检查：是否真的产生三类不同视角？是否有重复？主 agent是否保留证据？

## 13. 第二次练习：串并行混合流水线

设计但先不实施以下流程：

```text
阶段 1（并行只读）：调用链调查 + 测试缺口审计
阶段 2（主 agent）：汇总并由用户确认根因/规格
阶段 3（单写者）：实现最小修复
阶段 4（并行只读）：正确性 review + 测试 review
阶段 5（主 agent）：裁决、修改、运行集成验证
```

为每个 agent 写六要素委派契约，并画出依赖关系。若两个 agent需要同一文件写权限，修改设计直到所有权清楚。

## 14. 阶段 C 综合验收

完成一个复杂任务的“计划与协作演练”，不要求真正开发大型功能，但必须提交：

- 经过需求访谈的规格；
- 带验证和停止条件的计划；
- 聊天拓扑选择及理由；
- compact 前后或手工交接对账；
- 两次持久检查点；
- 至少两个有界只读 subagent 或独立聊天结果；
- 主 agent 的去重、冲突裁决和覆盖审计；
- 一次中断/失败恢复；
- 最终逐项完成审计。

## 评分表

每项 0–2 分，共 20 分：

| 项目 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 规格 | 模糊想法 | 有部分行为 | 用户、边界、错误、范围外、验收完整 |
| 计划 | 动作清单 | 有顺序 | 每步有结果、证据、风险和停止条件 |
| 动态更新 | 不更新 | 口头变化 | 新事实触发正式计划调整 |
| 聊天结构 | 全塞一个聊天 | 大致拆分 | new/fork/side/compact 选择有证据 |
| 持久化 | 只靠记忆 | 有摘要 | 文件检查点可独立恢复 |
| 恢复 | 重头开始 | 简单继续 | 对账文件、进程、产物后最小继续 |
| 委派 | 宽泛重复 | 有角色 | 六要素齐全且子任务独立 |
| 写入隔离 | 冲突编辑 | 口头避免 | 单写者或独立 worktree/所有权明确 |
| 汇总 | 拼接报告 | 有总结 | 去重、冲突实验、跨组件覆盖完整 |
| 完成审计 | 凭感觉 | 看部分测试 | 原始要求逐项对应权威证据 |

达到 16 分，且“恢复、委派、写入隔离、完成审计”均不为 0，阶段 C 通过。
