# 06：从错误现象到根因诊断

## 本课目标

把“测试挂了，帮我看看”升级为可重复、可证明的诊断流程。你将学会区分症状、触发条件、错误传播点和根因，并控制 Codex 不要未经授权直接修改。

## 1. 四个容易混淆的概念

| 概念 | 含义 | 例子 |
|---|---|---|
| 症状 | 用户最终看见的异常 | 识别结果为空 |
| 触发条件 | 使问题出现的输入或环境 | 波形长度小于一帧 |
| 错误传播点 | 异常状态被观察到的位置 | 解码器收到零帧 logits |
| 根因 | 最早违反正确性约束的位置 | 前端没有处理过短音频 |

堆栈最顶层常是错误传播点，不一定是根因。只在最后一层加 `try/except`，可能隐藏问题而不解决它。

## 2. 标准诊断漏斗

```text
确认预期行为
→ 建立稳定复现
→ 缩小变量
→ 沿数据/控制流向前追踪
→ 找到最早错误状态
→ 形成可证伪假设
→ 用实验排除替代解释
→ 确认根因和影响范围
```

诊断阶段的产物不是补丁，而是一份证据充分的根因说明。

## 3. 先固定预期行为

很多“bug”其实是规格不清。先从以下来源确认期望：

1. 现有测试和公开接口；
2. 用户文档和示例；
3. 类型、错误信息和函数名；
4. 维护者或用户明确决定。

如果来源互相冲突，Codex 应报告冲突，而不是挑一个最方便实现的答案。

## 4. 高质量复现包含什么

复现至少记录：

- 精确命令或操作步骤；
- 输入样本；
- 环境和关键版本；
- 期望结果；
- 实际结果；
- 是否稳定发生；
- 退出码、堆栈或最小输出。

示例：

```text
命令：uv run python -m unittest tests.test_acoustic_engine.DecoderTests.test_blank_separates_repeated_tokens
期望：测试通过，blank 分隔的重复 token 保留两次。
实际：断言失败，输出只有一个 token。
频率：连续运行 3 次均失败。
```

注意：上例是格式示范，不表示当前仓库真的失败。没有实际执行就不能声称复现。

## 5. 让假设可以被推翻

弱假设：“可能是解码器有问题。”

强假设：

```text
如果 StreamingGreedyDecoder 在 chunk 边界错误重置 previous_id，
那么同一 token 分布在两个 chunk 时会被重复输出；单 chunk 输入应正常。
```

强假设同时给出机制和可观察预测。可以设计两个输入对照来证伪。

要求 Codex 建立假设表：

| 假设 | 支持证据 | 反对证据 | 下一实验 | 状态 |
|---|---|---|---|---|
| chunk 间状态被清空 | 只在跨 chunk 失败 | `reset()` 未显式调用 | 检查两次 `accept` 后状态 | 待验证 |

表格不是为了形式感，而是防止 Codex 爱上第一个解释。

## 6. 二分和最小化

复杂问题可通过减少变量定位：

- 真实音频换成合成短张量；
- 完整服务换成直接函数调用；
- 批量输入缩到一个样本；
- GPU 换 CPU；
- 并发改成串行；
- 大配置缩成最小配置；
- 对比工作版本与当前版本。

最小复现必须保留原问题的关键机制。把问题“简化没了”不能证明根因。

## 7. 诊断提示词模板

```text
只诊断，不修改文件。

现象：<完整描述>
复现：<命令、输入、期望、实际>
上下文：<相关文件或最近变化；不知道时明确说不知道>
约束：不训练、不联网、不改测试；允许创建临时的最小复现但不要提交产物。

请先亲自复现。区分症状、触发条件、错误传播点和根因；
建立多个可证伪假设并用最小实验排除。沿调用链找到最早错误状态。
完成时给出：根因、证据、影响范围、未排除因素、最小修复方向。
无法复现时不要猜，说明环境差异和下一项最有信息量的检查。
```

## 8. 什么时候授权修复

根因确认后，单独发出修改请求：

```text
根据已确认的根因实施修复。保持 <公开契约> 不变，避免无关重构。
先新增或确认一项在修复前失败的回归测试，再修改实现；
修复后重新运行原始复现、回归测试和最近相关测试。
审查完整 diff，禁止通过删除测试、降低断言或吞掉异常制造通过。
```

对难以安全创建“修复前失败”测试的情形，可以记录证明缺口并使用最强的可重复验证，不能伪造红绿过程。

## 9. 常见假修复

### 吞异常

```python
try:
    risky_operation()
except Exception:
    pass
```

表面不报错，数据可能仍然错误。

### 扩大容忍范围

测试期待精确结果，却把断言改成“差不多”或直接删除。

### 只修测试夹具

生产路径仍有 bug，但测试输入被改得不再触发。

### 在错误层补默认值

上游生成非法状态，下游用空值掩盖，真正契约继续被破坏。

### 顺手重构

同时改大量结构，使得无法判断哪项变化真正修复了问题。

## 10. 实战：受控诊断演练

不要破坏主项目。让 Codex先选一个已有、快速、纯函数测试，例如 `DecoderTests` 中的测试，并提出一个**仅用于学习的临时工作树改动方案**。你确认方案后才执行：

```text
我要练习诊断。请先不要改文件。
从 tests/test_acoustic_engine.py 的 DecoderTests 中选择一个运行快速、
不会触发模型训练或网络的测试。提出一个最小、可逆、不会涉及数据文件的临时 bug 注入方案，
说明预期失败、恢复方法和精确影响范围。等我确认后再注入。
```

确认后按三阶段进行：

1. 对话 A 注入 bug 并记录精确 diff；
2. 新对话 B 只得到症状和复现命令，完成盲诊断与修复；
3. 你比较 B 的根因结论与 A 的真实改动，运行测试并确认 diff 已恢复正确状态。

如果你不熟悉 Git 或无法确保恢复，就采用无写入版本：让 Codex阅读测试，虚构一个与代码一致的故障场景，再只写诊断计划，不实际注入。

## 11. 诊断报告模板

```text
症状：

最早错误状态：
已确认根因：
关键证据：
被排除的假设：
影响范围：
最小修复方向：
尚未验证：
```

## 本课验收

你必须提交一份诊断报告，并满足：

- 有实际复现或明确写出无法复现；
- 至少比较两个假设；
- 根因是最早错误状态，不只是最终异常位置；
- 诊断阶段没有未经授权修改生产代码；
- 修复后同一复现和相关测试均有结果；
- 未通过删除测试或降低断言获得绿色。

口试：解释“测试失败的位置为什么不一定是根因”，并给出一个能推翻自己首选假设的实验。
