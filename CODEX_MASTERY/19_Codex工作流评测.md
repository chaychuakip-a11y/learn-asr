# 19：用评测而不是感觉优化 Codex

## 本课目标

“这个模型好像更聪明”“这个提示词感觉更稳”都不是可靠结论。本课教你建立小型 golden task set，对提示词、Skill、模型、推理强度或工作流做可重复比较，并统计成功率、回归、成本和人工修正量。

## 1. 先定义你在评测什么

评测对象可能是：

- 两个提示词模板；
- 有/无 `AGENTS.md`；
- Skill 的 description 或流程版本；
- 单 agent 与多 agent；
- 两个模型或推理强度；
- 有/无计划模式；
- 自动化版本；
- review 规则。

一次实验尽量只改变一个主要变量，否则无法归因。

## 2. 从真实失败建立任务集

Golden task set 应来自真实工作，而不是只挑容易题。至少包括：

- 典型任务；
- 边界任务；
- 信息不足、应追问的任务；
- 不应修改的只读任务；
- 有旧有失败或脏工作树的任务；
- 安全/权限边界；
- 应拒绝或停止的任务；
- 负例：不应触发某 Skill/工具。

保留失败样本比只保存成功 demo 更有价值。

## 3. 任务规范必须冻结

每个案例记录：

```text
case_id：
仓库提交/fixture：
用户提示：
可见上下文：
允许权限和工具：
期望行为：
禁止行为：
完成标准：
评分方法：自动 / 人工 / 混合
```

如果 A 方案看到更多文件、获得网络，而 B 没有，比较结果不公平。

## 4. 指标分层

### 结果正确性

- 功能是否满足；
- 测试是否直接覆盖需求；
- finding 是否真实；
- 只读任务是否保持无修改。

### 过程可靠性

- 是否先调查；
- 是否保护用户改动；
- 是否遵守权限；
- 是否报告证明缺口；
- 是否在失败后正确恢复。

### 效率

- 墙钟时间；
- token 或调用量；
- 工具调用数；
- 重试次数；
- 人工澄清和纠偏次数。

### 可维护性

- diff 大小和无关变化；
- 代码/文档风格；
- 测试脆弱性；
- 后续 review 发现数量。

不能只看“最终测试绿了”。

## 5. 二元通过与分项评分

硬门槛适合：

- 未授权外部写入：立即失败；
- 删除用户改动：立即失败；
- 必须测试未运行：失败；
- 公开 API 被破坏：失败。

分项评分适合质量差异：

| 维度 | 0 | 1 | 2 |
|---|---|---|---|
| 根因 | 猜测 | 定位错误附近 | 证据证明最早错误状态 |
| 测试 | 无/弱化 | 相关测试通过 | 红绿回归 + 相邻覆盖 |
| 范围 | 大量无关改动 | 少量噪音 | 最小一致性 diff |
| 汇报 | 声称完成 | 有命令 | 证据、退出码、缺口完整 |

先定义 rubric，再看输出，避免根据喜欢的答案临时改标准。

## 6. 自动检查与人工评审

适合自动：

- 测试/编译/类型检查；
- 文件变化范围；
- JSON schema；
- 是否出现敏感模式；
- 运行时间和退出码；
- 是否触发正确工具。

需要人工或独立 reviewer：

- 需求理解；
- 架构合理性；
- finding 可利用性；
- 证明是否足够；
- 用户体验；
- 报告是否夸大。

自动测试覆盖不到的质量不能被“green”吞掉。

## 7. 盲评和随机化

为了减少偏见：

- 隐藏方案名称，用 A/B；
- 随机输出顺序；
- reviewer 不看谁生成；
- 同一 rubric；
- 多案例，而非一个成功 demo；
- 高风险结论由第二人或独立聊天复核。

同一个模型审查自己刚写的方案可能有确认偏误。至少使用独立上下文。

## 8. 随机性与重复次数

Agent 运行具有随机性和环境变化。单次结果不能代表稳定性。小型学习评测可每个案例运行 2–3 次；高要求评测需要更多样本和置信区间。

记录：

- 每次独立 run；
- 同一环境与提交；
- 成功/失败和失败类型；
- 中位数而非只报最好速度；
- 极端值和原因；
- 缓存或预热影响。

不要为了“结果稳定”丢弃失败 run。

## 9. 成功率不够

假设两个方案都 80% 成功：

- A 失败时只漏文档；
- B 失败时删除用户数据。

它们风险完全不同。需要失败分类和严重度：

- 理解错误；
- 调查不足；
- 工具失败；
- 修改错误；
- 测试空洞；
- 权限越界；
- 虚假完成；
- 上下文丢失；
- 环境不可复现。

## 10. Precision、recall 与工具触发

评测 Skill、Plugin 或 MCP metadata 时：

- precision：触发时有多少次真的应该触发；
- recall：应该触发的案例有多少被触发；
- negative accuracy：不该触发时是否保持不触发。

先保证负例 precision，避免工具乱调用或误写外部状态，再追求边缘召回。

## 11. 成本指标

记录：

- 输入/输出 token；
- 模型和推理强度；
- subagent 数量；
- 工具调用和昂贵命令；
- 墙钟时间；
- 人工等待与修正时间；
- 失败后的返工成本。

便宜但经常需要人工修正的方案，整体成本可能更高。

## 13. 防止评测污染

- 不在调参时反复查看 holdout 答案；
- 训练集用于迭代，holdout 用于最终验证；
- 新发现真实失败加入未来回归集；
- 不删除难例来提高成功率；
- 记录案例版本变化；
- 测试代码和评分器也要 review。

在个人学习中可以简单分成 8 个开发案例 + 2 个保留案例。

## 14. 实战一：模糊提示 vs GCCD

准备 6 个小任务，覆盖解释、诊断、修改、审查、信息不足和安全边界。比较：

```text
A：一句模糊请求，例如“测试坏了，修一下”。
B：同一目标的 GCCD 版本，包含复现、约束和完成标准。
```

控制：同一仓库提交、同一模型/强度、同一权限、新聊天、每例至少两次。

评分：

- 是否先复现；
- 根因质量；
- diff 范围；
- 测试证据；
- 是否越权；
- 人工追问数；
- 总时间。

预先写下假设，不要事后挑对 B 有利的指标。

## 15. 实战二：单 agent vs 有界 subagent

选择一个真正可并行的只读审查任务。A 使用单 agent；B 使用三个有界 subagent。比较：

- 独立高价值 finding 数；
- 重复 finding；
- 错误 finding；
- 证据完整性；
- token、时间和汇总成本；
- 是否发生范围漂移。

若 B 没有显著提高质量或速度，就不应为了“高级”而默认多 agent。

## 16. 评测报告模板

```text
结论：在 <任务分布和环境> 下，方案 B 相对 A 的变化。
任务集：
主要变量：
硬门槛失败：
分项得分与不确定性：
失败类型：
时间/token/人工成本：
最重要失败样本：
适用范围：
不能外推到：
采纳与回退条件：
```

避免“B 永远更好”。结论只适用于测试过的任务、环境和版本。

## 17. 常见评测错误

- 用一个案例得出普遍结论；
- A/B 上下文或权限不同；
- 先看结果再定义评分；
- 只报最好一次；
- 把测试通过当唯一指标；
- reviewer 知道方案身份；
- 调参集与最终验证集相同；
- 忽略 token、人工修正和风险严重度；
- 产品或模型更新后仍沿用旧结论。

## 本课验收

完成一次至少 6 个案例、每方案每例至少 2 次的小型 A/B 评测。必须提交：冻结任务集、rubric、控制变量、原始 run 记录、失败分类、成本、盲评和有限范围结论。

口试：

1. 为什么单次成功不能证明工作流稳定？
2. 为什么先写 rubric？
3. Precision 和 recall 如何用于工具触发？
4. 两个相同成功率方案为什么风险可能不同？
5. 如何避免为了提高分数污染评测集？

能依据失败样本拒绝一个“平均分更高但高风险失败更多”的方案，才算掌握评测。
